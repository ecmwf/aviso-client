# aviso-client suite, plan v0.3

Client suite for [`aviso-server`](https://github.com/ecmwf/aviso-server), ECMWF's notification service for data-driven workflows. Three surfaces (Rust library, Rust CLI, Python package via PyO3) over one core implementation.

This is the current plan. Architectural decisions referenced by id (`D1`, `D2`, and so on) are defined in [`decisions.md`](./decisions.md).

---

## 1. Server-side facts that drive design

All verified from the `aviso-server` source. These constraints determine the client architecture.

| Concern | Reality on the server | Client implication |
|---|---|---|
| SSE event format | `event: <type>\ndata: <json>\n\n`, **no `id:` line** | Standard `Last-Event-ID` reconnect does not apply. Sequence is extracted from the CloudEvent `id` field. |
| Resume parameters | `from_id` (inclusive sequence) and `from_date`, mutually exclusive, in the POST body | Persist `(stream_key, last_committed_sequence)`; reconnect with `from_id = last_committed_sequence + 1`. |
| Connection lifetime | Server intentionally closes after `connection_max_duration_sec` (default 3600 s), emitting `connection-closing` with `reason: "max_duration_reached"`. Other reasons: `server_shutdown`, `end_of_stream`. | Reconnects are routine, not failures. Must NOT trigger error backoff. |
| Heartbeats | `heartbeat` event every `sse_heartbeat_interval_sec` (default 30 s). | Monitor liveness; absence beyond `max(3 × interval, interval + 30 s)` triggers a reconnect. |
| Event types on the wire | `live-notification`, `replay`, `heartbeat`, `connection-closing`, `error`, `replay-control` | Six frame kinds; client uses a typed model. |
| Correlation | `X-Request-ID` header on every response, also embedded in the first SSE event and every error/control payload | Surface in client logs so users can quote it when filing issues. |
| Endpoints | `POST /api/v1/notification`, `POST /api/v1/watch`, `POST /api/v1/replay`, `GET /api/v1/schema[/{event_type}]`, `DELETE /api/v1/admin/{wipe/stream,wipe/all,notification/{id}}`, `GET /health`, `GET /metrics` (separate port) | Small, stable surface. |
| Auth | OpenAPI declares `bearer_jwt` and `basic`; server `direct` mode forwards Basic to auth-o-tron, `trusted_proxy` mode validates Bearer JWT locally | Client supports both Basic and Bearer; sources composable (env, file, explicit). |
| Schemas | `GET /api/v1/schema` returns identifier rules per stream | Discovery only (no client-side validation; the server is the single source of truth). |
| Wire payload | CloudEvent JSON. Each notification has `id = <event_type>@<sequence>`, `source = base_url`, `type = int.ecmwf.aviso.<event_type>`, `time`, `data = {identifier, payload}` | Client hides the CloudEvent envelope; users see a `Notification` type. Sequence is parsed from `id` via `rsplit_once('@')`. |

## 2. Architecture summary

Cited by ADR id; full rationale in [`decisions.md`](./decisions.md).

- **D1**: one Rust core (`aviso`), two peer consumers: the `aviso-cli` Rust binary and the `aviso-py` PyO3 extension. Core never depends on actix, PyO3, or CLI machinery.
- **D2**: reconnect-as-norm with at-least-once delivery. Per-resume-key `last_committed_sequence` advances only after all required triggers succeed. Watch state machine is `ReplayPhase × ConnectionStatus`, single reducer.
- **D3**: resume key is a hash of normalized base URL, event type, canonical filter body, schema fingerprint, key format version.
- **D4**: `StateStore` trait. `MemoryStore` plus a single-process `JsonFileStore` (atomic temp-write and `fsync`) ship in Phase 2 so the CLI can resume across restarts. Multi-process hardening (advisory file lock and monotonic-cursor merge) defers to Phase 3. The trait is the extension point; no other backends are planned.
- **D5**: `reqwest` with `rustls-tls`. SSE via the owned parser-only `crates/finesse` (WHATWG conformant, sync push-based, no I/O); our own reconnect loop (high-level SSE crates assume `Last-Event-ID`, which aviso does not honour).
- **D6**: `tokio`.
- **D7**: no client-side schema validation. Server is the single source of truth; client surfaces server errors verbatim with `X-Request-ID` correlation. `GET /api/v1/schema` is exposed only for human discovery (`aviso schema list`/`get`).
- **D8**: `AuthProvider` async trait. `Basic`, `Bearer`, `Env`, `ConfigFile`, `Chain`. Refresh on 401, retry once. Tokens never logged. Env prefix `AVISO_*`.
- **D9**: CloudEvent envelope hidden. Sequence from `<event_type>@<sequence>` via `rsplit_once('@')`. A malformed id is a terminal `ClientError::MalformedEvent`, not a reconnect (avoids livelock).
- **D10**: Rust public API is for Rust users; not constrained for hypothetical FFI. A C/C++ surface, if ever needed, is a separate adapter crate.
- **D11**: triggers shipping in the Rust core are `echo` (stdout), `log` (file), `command` (subprocess spawn), and `webhook` (HTTP POST with a templated body), implemented under `crates/aviso/src/watch/trigger/`. Dispatcher stays an internal `enum` (`TriggerKind`); no public trait. Required vs optional triggers; bounded retry via the supervisor's `compute_backoff`; required failure stops the listener. Per-trigger `timeout` and `fail_fast` deferred from the v1 (echo + log) PR are introduced with the trigger expansion (Phase 4): `timeout` is meaningful for command and webhook only (echo/log dispatch in microseconds and dropped the field); `fail_fast` is meaningful for webhook only (5xx retry vs 4xx terminal). YAML deserialisation lives in `crates/aviso/src/watch/trigger/yaml.rs` so the CLI and PyO3 binding share one schema. Echo and Log are designed as the in-process "see what is happening" pair; Command and Webhook are designed for declarative durable side effects (running downstream tooling, posting to Slack/Teams/Discord). The `function` trigger that pyaviso exposes is intentionally NOT in this list: `watch_with_handler` (the consumer-side handler we already expose) covers the in-process callback use case, and adding a redundant variant would split the surface.
- **D12**: logging per ECMWF Codex Observability.md. Libraries emit `tracing` events, the binary owns subscriber init, JSON to stderr, redaction at emission, single-boundary log discipline. Strict OTel formatter is a follow-up.
- **D13**: Apache-2.0; per-file ECMWF copyright headers are optional in v0.1.
- **D14**: metrics deferred. Reserved namespace `aviso_client_*` (kept distinct from `aviso_server_*` for joint scraping). Banned labels documented.
- **D15**: watch state machine is the orthogonal product `ReplayPhase × ConnectionStatus`, single reducer, fields private.
- **D16**: `notify()` is NOT auto-retried on ambiguous transport failure (avoids duplicate publish).
- **D17**: `from_date` is bootstrap-only; converts to sequence cursor after the first commit.

## 3. Phased roadmap

Each phase is sized for one PR or a tight series, with a real demo at the end. "Done" requires CI green on every check, not just the new feature.

### Phase 0. Bootstrap

- Workspace skeleton (`aviso`, `aviso-cli`, `aviso-py`), all building.
- mdBook skeleton with `SUMMARY.md` taxonomy.
- `pyproject.toml` (maturin backend, scaffold).
- CI: `cargo fmt --check`, `cargo clippy --locked -D warnings`, `cargo test --locked`, `mdbook build`, `mdbook test`, `cargo deny check`, `docker compose config`.
- `tests/e2e/` docker-compose pointing at the prebuilt ECMWF aviso-server image (`eccr.ecmwf.int/aviso/aviso_server:0.6.2`), with a mounted test config that disables auth, pins the in-memory backend, and shortens heartbeat and connection-lifetime to surface reconnect bugs quickly. `AVISOSERVER_APPLICATION__BASE_URL` tracks `AVISO_SERVER_HOST_PORT` so parallel shards stay self-consistent.
- AGENTS.md rules: lints/errors/typing/ownership rules from the start, plus the time-bound-references rule (phase numbers live only in `plans/`) and conventional-commits rule (one concern per commit, every commit on `main` passes the full check set).
- First ADR set (D1 through D17).

Out of scope: any client behaviour. **Done when**: a fresh clone passes the CI commands above.

### Phase 1. Rust core (non-streaming)

- `AvisoClient`: `notify`, `schema`, `schema/{event_type}` pass-through, admin endpoints.
- `AuthProvider` (async) plus `Basic`, `Bearer`, `Env`, `ConfigFile`, `Chain`.
- `ClientError` (thiserror) with `X-Request-ID` correlation surfaced.
- `Notification` and `NotificationRequest` types; CloudEvent sequence extraction.
- Conservative `notify()` retry policy (D16).

Tested with `wiremock`. Property tests on CloudEvent id parsing. Docs for usage and auth.

### Phase 2. Streaming and checkpoint semantics

- Owned WHATWG SSE parser in a workspace crate (`crates/finesse`, named for the SSE that hides in the middle of the word, `publish = false` until a second consumer materialises) behind our own typed `SseEvent` enum. The existing parser-only crates on crates.io are either too fresh to depend on (`sse-core`, three weeks old at the time of decision, 63 downloads), maintenance-cold for four years (`eventsource-stream`, `async-sse`), or wrap their own reconnect logic that conflicts with our resume model (`reqwest-eventsource`, `eventsource-client`). `sse-codec` (MPL-2.0, 300k recent downloads, last release 2026-02-12) is the one viable third-party option; we picked the owned route to keep the critical path under our control and to give the parser room to evolve with `aviso-server`'s event taxonomy. D5 is amended to name the owned `finesse` crate.
- Reconnect supervisor with the classifier (D2). Single-boundary log discipline.
- Watch state machine per D2 and D15.
- `StateStore` trait plus `MemoryStore` plus a single-process `JsonFileStore` (atomic temp-write and `fsync`, but no cross-process locking yet). Pulled forward from Phase 3 because the CLI needs file-backed resume from day one: a user who runs `aviso watch`, stops the binary, and runs it again expects to pick up at the last committed sequence, not to start over. D4 amended in the same PR.
- `HistoryGap` typed error from `notification_replay_limit_reached`.
- Trigger dispatcher plus `Echo` and `Log` (D11), wired into checkpoint policy.
- Observability via `tracing` events at every state transition (connection open, connection close with reason, heartbeat starvation, replay phase boundaries, trigger outcomes, fatal). No client-side metrics surface; D14 is amended from "reserved namespace, deferred impl" to "tracing-only; metrics are a consumer concern". If a real consumer later needs a Prometheus or OTel metrics facade, it lands as a small opt-in follow-up against the `metrics` crate facade, not as a hard dependency.


Tested with a `wiremock` chunked-response harness plus kill-every-200ms stress, heartbeat-starvation, drop-during-replay, schema-fingerprint-change, replay-limit-mid-stream tests.

Public streaming API is **not** declared stable here. That happens at the end of Phase 3.

### Phase 3. Resume persistence: multi-process hardening

The single-process `JsonFileStore` (atomic temp-write plus `fsync`) ships in Phase 2 so the CLI works from day one. Phase 3 takes the multi-process correctness work that was originally bundled with it:

- Cross-process advisory file lock (`fs2` or `fd-lock`).
- Monotonic-cursor merge: before overwriting a key, read the on-disk checkpoint and commit only if the new sequence is at least the existing one. Protects against two processes racing on the same key.
- Kill-during-write fuzz harness: spawn N processes that write concurrently, SIGKILL them mid-write, assert the file always parses and no checkpoint goes backwards.
- `client.resume.applied` `INFO` log on resume from stored state.

Done when streaming API is stable; Phase 2 and Phase 3 tests all pass.

### Phase 4. Trigger expansion (command + webhook; email deferred)

Two new trigger kinds beyond the `echo` and `log` that shipped in Phase 2, plus a YAML serialisation surface for the upcoming CLI. Designed fresh for the Rust client; we read prior art for use cases (operators shell out to downstream tooling, ops teams want event notifications in Slack/Teams/Discord) but the API shape is whatever is cleanest in Rust. No commitment to wire-compatibility with the Python `pyaviso` package. No dependency on proprietary HTTP delivery APIs (AWS SES, SendGrid, Mailgun, etc.) per the user's no-managed-services stance in §7.2: every trigger uses operator-configured generic protocols.

- `Trigger::command(cmd)`: **shipped via PR-G1**. Spawn a child process via `tokio::process::Command` with the notification's identifier and payload fields exposed as `AVISO_*` environment variables, plus the full notification JSON as `AVISO_NOTIFICATION_JSON`. Builder: `.env(k, v)` (extra env), `.working_dir(p)`, `.timeout(Duration)` (now meaningful because `Child::kill().await` interrupts cleanly), `.retries(u32)`, `.required(bool)`, `.fail_fast(bool)`. Error variant: `TriggerError::Command { exit_code, stderr_tail }` (stderr ring buffer, last 4 KiB). POSIX-only via `/bin/sh -c`; the API surface is gated behind `#[cfg(unix)]`. Companion template engine shipped alongside (notification + env namespaces; resolution rules per §5 Resolved Phase 4 trigger expansion T2; raw template stays out of public errors). See §6 status snapshot for the merge details.
- `Trigger::webhook(url)`: **shipped via PR-G2**. Generic HTTP request (method overridable) to a user-configured URL. Builder: `.method(HttpMethod)`, `.header(k, v)` (multiple, header values templated; header names literal), `.body_template(impl Into<String>)`, `.timeout(Duration)`, `.retries(u32)`, `.fail_fast(bool)`, `.required(bool)`. URL, header values, and body all run through the in-crate template engine. Default body when `body_template` omitted is the full notification as compact JSON. Default `Content-Type` is `application/json` when the user has not set one. Default per-trigger timeout is 30 seconds (public constant `DEFAULT_WEBHOOK_TIMEOUT`). Built on the supervisor's existing `reqwest::Client`, so TLS knobs inherit naturally. HTTP-status-aware retry classifier: 5xx retryable, 4xx terminal when `fail_fast = true` (the default); `fail_fast = false` retries every error. Errors: `TriggerError::Webhook { status, body_tail }` (4 KiB body tail captured via streaming `Response::chunk()`) plus `TriggerError::WebhookBuild { reason }` (added during Copilot review for HTTP-client builder rejections; terminal under fail_fast=true). See §6 status snapshot for the merge details.
- YAML trigger config (`crates/aviso/src/watch/trigger/yaml.rs`): **shipped via PR-G2**. Serde-tagged `TriggerConfig` enum on `type:` with four `#[non_exhaustive]` payload structs (`EchoConfig`, `LogConfig`, `CommandTriggerConfig` Unix-only, `WebhookTriggerConfig`), each carrying `#[serde(deny_unknown_fields)]` (workaround for serde-rs issue #2123). Duration fields use `humantime_serde::option`. `TriggerConfig::into_trigger` consumes the config and produces a strongly-typed `Trigger` builder. Used by Phase 5 (CLI) and Phase 6 (PyO3) consumers; lives in the core crate so both surfaces parse the same schema.
- D11 amended twice (PR-G1 dated `*Amendment, 2026-05-22*` for command + template engine; PR-G2 dated `*Amendment, 2026-06-09*` for webhook + YAML deserialiser + secret-redaction discipline). The four shipped trigger kinds (echo, log, command, webhook) are now enumerated in the ADR.
- `Trigger::email(EmailConfig)`: **deferred** (originally planned as PR-G3). The high-level direction is locked in §5 Resolved "Phase 4 email trigger direction" E1-E6 (lettre backend, operator-configured SMTP, cross-platform, retry classifier extension); the design notes are preserved verbatim for when the work is picked up. Demoted to §4 Follow-ups carried forward. Reason for deferral: scope and prioritisation. Phase 4's two HTTP-and-process triggers cover the common operator workflows (Slack/Teams/Discord via webhook; downstream shell tooling via command), and the CLI work (Phase 5) is more valuable to unblock than a third trigger kind for the initial release.

Out of scope: email and AWS SNS delivery (both captured in §4 follow-ups); AWS SES / SendGrid / Mailgun and any proprietary HTTP delivery APIs (excluded by user stance in §7.2); in-process closure/function trigger (`watch_with_handler` already serves this use case); parallel trigger dispatch (still sequential per the existing trigger PR's Q5 decision); Windows shell for `command` (the API surface is `#[cfg(unix)]`-gated; native Windows support is not on the roadmap). Phase 4 is done with command + webhook + YAML deserialiser + D11 amendments.

Two PRs total in the phase: PR-G1 (`feat/trigger-command`, shipped, ~1500 LOC), PR-G2 (`feat/trigger-webhook`, shipped, ~2200 net LOC including the YAML deserialiser).

### Phase 5. Rust CLI

- Subcommands: `notify`, `listen`, `replay`, `schema {list,get}`, `admin {wipe-stream,wipe-all,delete}`, `config dump --redact`, `completions <SHELL>`. (`auth check` deferred to v2 per granular settlement Amendment J; tracked in §4 follow-ups pending a server-side `/api/v1/auth/check` endpoint.)
- YAML config plus `AVISO_CLIENT_CONFIG_FILE` override plus `AVISO_CLIENT_*` nested env vars.
- Default config file: `~/.config/aviso/config.yaml`.
- Default state file: `~/.config/aviso/state.json` (consumed by `JsonFileStore` from Phase 2). Both paths overridable via flags (`--config <path>`, `--state-file <path>`) and env vars (`AVISO_CLIENT_CONFIG_FILE`, `AVISO_STATE_FILE`). One directory for both config and state by design: simpler, one place to back up, consistent across Linux / macOS / Windows even where each platform has its own native convention.
- `--yes` required for destructive admin commands.
- `--ca-bundle <path>` for dev TLS; `--danger-accept-invalid-certs` loudly named with a WARN log.
- Graceful shutdown via cancellation tokens.
- YAML `triggers:` list per listener config wired through the `TriggerConfig` deserialiser from Phase 4 (all four kinds available from YAML).
- Top-level `listeners:` LIST in the config (pyaviso-compatible shape with `request` renamed to `identifiers`). `aviso listen [LISTENER_FILE...]` accepts a variadic positional list of listener YAML files (each with its own top-level `listeners:` list); positional files REPLACE the global config's `listeners:` section for that invocation. With no positional, falls back to the global config's `listeners:` section; if both are empty, exits 2 with a helpful stderr message naming both paths checked. `aviso listen` and `aviso replay` emit nothing on stdout; triggers handle output (operators add `- type: echo` to a listener's triggers if they want stdout NDJSON). Verbosity is `-v` count flag (`-v` = DEBUG, `-vv` = TRACE; no `-d`). `--config` gains `-c` short alias. Full design lives in §5 Resolved "Phase 5 CLI granular settlement".

Tested with `assert_cmd`.

### Phase 6. PyO3 extension

No Python-callable / function-trigger variant; in-process callbacks use `watch_with_handler` (already a Rust-side surface).

Ends with one Linux wheel built in CI plus an import-smoke test.

## 4. Follow-ups carried forward

Surfaced by the Oracle reviews and reflected in the roadmap. None gate any phase boundary; they are quality and scope items to revisit when the moment is right.

- `mdbook-linkcheck` (or an equivalent guard) so a broken cross-page anchor fails CI instead of being found by hand.
- Windows on the CI matrix, when the first platform-sensitive code lands (file locking, paths, signal handling). Required by Phase 7 wheels regardless.
- Strict OpenTelemetry-aligned log formatter. The current CLI emits `tracing_subscriber::fmt::json()` which uses tracing's own schema. Pick OTel-shaped JSON when a consumer requires it.
- Per-file ECMWF copyright headers, if ECMWF policy requires them. Currently the LICENSE file plus SPDX in each `Cargo.toml` carries the licensing.
- A server-side replay-summary signal carrying `{requested_cursor, oldest_available_sequence, replayed_count, complete: bool}`, to revisit only if replay observability hits a real ceiling. The client ships in "completeness unknown" mode without it and degrades cleanly. (A validator-version response header was considered too; it is moot now that D7 dropped client-side validation.)
- Idempotency-key contract for `POST /api/v1/notification`. Without it the client refuses to auto-retry ambiguous transport failures (D16).
- An `AVISO_LOG` malformed-directive test once the CLI has runtime tests.
- Operator-facing ingress configuration recipe for the watch endpoint. Verified working with k8s nginx ingress at `nginx.org/proxy-buffering: "false"`, `nginx.org/proxy-read-timeout: 3600s`, `nginx.org/proxy-send-timeout: 3600s`. The buffering knob is mandatory: nginx will otherwise buffer the SSE body until "complete" and the client will receive nothing until the connection closes. The two timeouts should match the server's `connection_max_duration_sec`. Shipped in PR-E2b's docs touch; reference for future operators.

- Resilience-layer lessons surfaced during PR-E2b code review that the original PR-E2b plan did not pre-empt. Document for the PR-F plan author to mirror:
  - Backoff `attempt` index is 0-based ("attempt 0" is the first retry, window `[0, BASE_DELAY_MS)`); the supervisor's `retry_counter` is failures-since-last-success, so callers pass `retry_counter.saturating_sub(1)` not `retry_counter`. PR-F's per-trigger retry calculator should follow the same indexing convention.
  - `Instant::now() + budget` panics if `budget` saturates `Duration::MAX`. Any time-bounded operation in future trigger work (Webhook-trigger timeout, retry backoff sleep) must either compute the deadline with `checked_add` or cap the input duration; the resilience layer caps the heartbeat budget at `u32::MAX` seconds. The v1 trigger PR has no per-attempt timeout (see §5 Resolved Q6 amendment) so this is forward-looking guidance for the next trigger PR.
  - Cancel-safety asymmetry is real and needs explicit documentation per operation: in PR-E2b, `StateStore::get` races against cancellation while `StateStore::put` runs to completion; the trait docstring spells the asymmetric contract on both sides. PR-F's trigger trait/enum should make the same explicit decision for each dispatch and document it on the consumer-side surface.
  - `is_success()` is the wrong gate for any contract that requires a specific HTTP status; use `status == StatusCode::OK` (or the specific code) and route everything else through the typed error path. PR-F has no HTTP gates by itself, but if the trigger dispatcher ever issues an HTTP webhook, this lesson applies.
  - Bounded channels with capacity > 1 break "pulling N+1 implies N is durable" if the commit happens supervisor-side before the consumer pull. The interim PR-F framing in the PR-E2b plan implied a checkpoint-policy swap from "commit on next send" to "commit after triggers succeed"; the PR-F design discussion ultimately preserved the PR-E2b commit-on-next-send mechanism for exactly this reason (see §5 Resolved "PR-F trigger design / Commit timing under triggers"). Future PRs touching commit semantics must consider channel-capacity implications first.
  - Test-helper RAII over `std::mem::forget` for keeping channel senders alive. Return the sender from the helper and let the test scope own it. The Copilot review on PR-E2b flagged this and it took a small refactor; PR-F's tests should use the same pattern from day one.

- AWS SNS trigger as a future Trigger variant. Idea: deliver the notification (CloudEvents-shaped or arbitrary body template) to an AWS SNS topic ARN, including FIFO topics with `MessageDeduplicationId` derived from the CloudEvents id. Would need either the `aws-sdk-sns` crate (heavy dep) or manual SigV4 HTTP signing against the SNS endpoint. NOT scheduled, no current ECMWF user asking for it; captured here in case the demand surfaces. Lands as a third HTTP-flavoured trigger kind (alongside `webhook`) or as a delivery-mode option on `webhook` itself; settle the shape when the user appears.

- **Email trigger** (`Trigger::email(EmailConfig)`). Originally planned as PR-G3 inside Phase 4 alongside command and webhook; deferred during post-PR-G2 planning because the two HTTP-and-process triggers cover the common operator workflows and the CLI unlocks more user value than a third trigger kind for the initial release. The high-level direction is preserved verbatim in §5 Resolved "Phase 4 email trigger direction" E1-E6: lettre as the SMTP backend (cross-platform; rustls-tls; no system OpenSSL dep), operator-configured destinations (Gmail / Outlook / Office365 / ProtonMail Bridge / self-hosted Postfix / any RFC-5321 relay), credentials interpolated via `{{ env.<NAME> }}`, retry classifier extension marking `SmtpAuth` + `MalformedAddress` + permanent SMTP 5xx as terminal. The §7.9 "Pending in PR-G3 (email)" quick reference and the (now-removed) §7.11 PR-G3 compaction-survival checklist captured the granular settlement plan; the design notes are preserved so when the work is picked up, plan-time effort is minimal. Estimated ~1100 LOC + ~49 new tests when it lands. No specific scheduling commitment.

- **aviso-server `/api/v1/auth/check` endpoint** (server-side work, then `aviso auth check` CLI subcommand in v2). Originally planned as part of Phase 5's Q2 surface; deferred during the CLI design walk after the aviso-server investigation at commit `23fb4e9` revealed no existing auth-validation endpoint AND schema-list is anonymous (cannot serve as a credential-validation proxy). The server-side work item: add `GET /api/v1/auth/check` that runs through the existing `AuthMiddlewareService` then returns 200 with `{"status": "ok", "principal": "<user>", "roles": ["admin"|"user"]}` on success, or 401 on bad / missing creds. Cheap to implement (≈30 LOC in `aviso-server/src/routes/auth_check.rs` plus the route registration in `startup.rs`). Once shipped server-side, the corresponding `aviso auth check` CLI subcommand lands in a follow-up CLI PR (≈100 LOC: a thin handler that hits the endpoint, checks status, prints the principal + roles in the TTY-aware formatter). Until then, operators validate auth implicitly via `aviso listen` / `aviso notify` exit codes per Amendment J in the granular settlement.

## 5. Open questions

None gate any current work. Open questions tracked here so they remain visible across compactions.

### Not gating any current work

- Should `BlockingAvisoClient` provide a context-manager-only API, or also a plain class with explicit `close()`? Pick during the Phase 6 spike.
- When the Python bridge eventually wires logging, choose between `tracing_log` to `log` to `pyo3-log`, or a custom `tracing_subscriber::Layer` calling Python `logging` directly. Decide during Phase 6 based on backpressure and GIL behaviour.

### Resolved

- *Watch API shape*: settled as Stream-primary plus a thin `watch_with_handler` callback sugar that wraps the Stream. The Rust core exposes `impl Stream<Item = Result<Notification, ClientError>>` for idiomatic async iteration and a 20-line `watch_with_handler` for daemon-style consumers. Both surfaces drain the same internal `tokio::sync::mpsc` channel so reconnect, checkpoint, auth-refresh, heartbeat, and trigger behaviour stay identical across bindings. The decision is driven by the cross-language constraint that Python (PyO3, via `__aiter__`/`__anext__` over the channel) and a future C++ adapter (via callback registration on `watch_with_handler`) must both bind cleanly without reimplementing supervisor logic. The ADR for this decision (D19) lands with PR-E2a where the API ships.

- *Fan-out across consumers of a single watch*: settled as single-consumer. The supervisor uses `tokio::sync::mpsc::channel(N)` internally; `client.watch(req)` returns a `NotificationStream` that is not `Clone`. Anyone wanting one watch to feed multiple consumers can tee via `tokio::sync::broadcast` themselves. The single-consumer choice keeps checkpoint advancement and trigger semantics unambiguous (one consumer means one well-defined commit point) and keeps bindings simple (PyO3 and a future C++ adapter each bind one channel per call). A future broadcast-based API can ship later without breaking single-consumer callers if a concrete need surfaces. Captured by the same ADR D19 as the watch API shape.

- *Multi-listener support across a single `AvisoClient`*: one client can drive any number of concurrent `watch()` calls; each produces an independent supervisor with its own HTTP connection, checkpoint slot, and (in PR-F) trigger pipeline. Resource sharing happens cleanly at the appropriate layers (`reqwest::Client` connection pool, `Arc<dyn AuthProvider>` for shared auth state with refresh propagation, `Send + Sync` `StateStore` for per-key write serialisation). D3 guarantees per-listener resume-key uniqueness across distinct (event_type, filter, schema_fingerprint) tuples. PR-E2a keeps `AvisoClient` `Send + Sync + Clone`, logs a `WARN` on resume-key collision (a misuse signal, not a hard error), and ensures `AvisoClient::Drop` cancels all child supervisors via a parent `CancellationToken`. Server-side capacity policies (per-user, per-role) are out of the client's scope and handled at the proxy or aviso-server layer. The ADR for this decision (D20) lands with PR-E2a.

- *PyO3 spike timing*: settled as defer to Phase 6. The eight-test spike was insurance against the risk that a closure-heavy or lifetime-bound Rust API would not bind cleanly into Python's `asyncio` model. The Option C resolution above (Stream over `mpsc` channel) is the textbook PyO3 async pattern with explicit `pyo3-async-runtimes` support, so the design risk the spike was sized to surface is substantially eliminated. The three residual concerns (Stream `Drop` cleans up the supervisor task; channel is bounded for backpressure; supervisor uses the ambient runtime rather than spawning its own) become design constraints on PR-E2 rather than a separate validation PR. PR-E2b includes a Rust integration test asserting that dropping the Stream mid-iteration tears down the supervisor task within a bounded time.

- *PR-E2 split*: PR-E2 is split into PR-E2a and PR-E2b along the seam between the happy-path data path and the resilience layer. PR-E2a ships the public API (`WatchRequest`, `AvisoClient::watch`, `watch_with_handler`) plus the supervisor's single-connection happy path; PR-E2b adds the reconnect loop, auth refresh, heartbeat watchdog, HTTP-status mapping, and `StateStore` integration. Two medium PRs are preferable to one large one because the API shape gets reviewer feedback before the resilience layer is built on top of it, and because each PR fits inside a single review cadence. See §6 for the per-PR scope details.

- *Checkpoint advancement (PR-E2b mechanism, preserved by PR-F)*: supervisor-side, on next send. The supervisor holds the last-sent-but-not-yet-committed sequence; before sending item N+1 it commits item N to the `StateStore`. The user-facing "commit on next pull" contract holds: pulling item N+1 implies item N is durable. The PR-E2b plan framed this as an "interim policy" to be swapped in PR-F; the PR-F design discussion decided to preserve this mechanism unchanged because it is what makes "pull N+1 implies N committed" work under capacity-1 backpressure, and that contract is the foundation of at-least-once for raw `watch()` Stream consumers. PR-F adds triggers as a pre-send gate (required-trigger failure terminates before send, no commit) without changing the commit timing. See §5 Resolved "PR-F trigger design" for the full disposition.

- *Parent-cancellation primitive for `AvisoClient::Drop`*: `Arc<DropGuard>` wrapping `tokio::sync::watch::Sender<bool>`. The last-clone drop fires the watch; each supervisor holds a `watch::Receiver` and `select!`s on `wait_for(|v| *v)` alongside its per-stream oneshot. No new workspace dependency; tokio's `sync` feature already covers `watch`.

- *User-supplied `from` versus stored checkpoint*: user `from` always wins when supplied. The `StateStore` checkpoint is consulted only when `WatchRequest` has no `from`. At-least-once delivery is preserved at the `StateStore` layer (re-delivering a committed item just re-commits the same value); the "library does not second-guess the user's explicit request" contract is preserved at the API surface.

- *`Retry-After` header on 429 / 503*: honoured with a 5-minute sanity cap. Parse delta-seconds or HTTP-date; sleep at least `min(header_value, 5 minutes)`. Falls back to the standard exponential backoff schedule when the header is absent or unparseable.

- *Schema fingerprint detection*: deferred entirely. The auto-derived resume key uses `schema_fingerprint = None`. The server does not emit fingerprints on the wire (the `dataschema` URL is the same string every time), and D7 already says client-side validation is not the library's concern. The `FatalKind::SchemaFingerprintChanged` reducer variant stays as harmless producer-side dead code; it costs nothing because `#[non_exhaustive]` and can be removed in a later polish PR if it bothers anyone.

- *Auth refresh scope*: every fresh connection attempt (initial AND every reconnect) gets the D8 refresh-then-retry-once treatment. The reducer's `RefreshingAuth` state guards against infinite loops within a single attempt. Long-lived watches survive token expiry that happens during reconnect N; the alternative (initial-only) would terminate the watch unrecoverably when a token expires mid-session.

- *Backoff jitter*: full jitter, `delay = random_uniform(0, base * 2^attempt) capped at 30s`. Randomness sourced from `Instant::now().elapsed().subsec_nanos()` so no `rand` dep is added. Good enough for spreading retries; backoff jitter does not need cryptographic randomness.

- *Heartbeat watchdog*: ships in PR-E2b. Long-lived watches are the explicit target workload (days to weeks of uptime), and across that timescale every silent-stream-death failure mode hits at least once: NAT entry rotation (30 minutes to a few hours on common middleboxes), network change after laptop sleep, intermediate proxy restart, server-side application hang, and the routine `max_duration_reached` reconnect cycle (~170 reconnects per week at the 3600s default) where any one fresh connection can hit any of the above. TCP keepalive is structurally insufficient: even tuned aggressively via `reqwest::ClientBuilder::tcp_keepalive(30s)` the kernel needs `30s + 9 * 75s = 11.75 minutes` on Linux defaults to declare a connection dead, and it cannot see server-side hangs behind a healthy reverse proxy because the proxy's TCP stack keeps ACKing the keepalive probes. The watchdog wraps `response.chunk().await` in `tokio::time::timeout(max(3 * interval, interval + 30s))` per D2; on expiry the supervisor fires `WatchEvent::HeartbeatStarvation`, which the reducer maps to "reconnect with exponential backoff". Heartbeat interval is exposed as `AvisoClientBuilder::heartbeat_interval(Duration)` with a 30 s default (matching common `aviso-server` configurations; the exact server default is verified during implementation). The deadline is reset on every successful read of any non-empty chunk so quiet-but-healthy streams do not false-positive. No new workspace dep; `tokio::time` is already in scope.

- *PR-F trigger design*: resolved through a 12-question one-at-a-time discussion. The decisions below fix the public API shape, internal pipeline structure, and test surface for the trigger PR.

  - **Trigger timing (Q1)**: triggers run BEFORE the channel send. Supervisor pipeline per notification N is `receive N → run all configured triggers → send N on channel`. The consumer never sees an item whose required triggers have not all passed. Simplest semantics. Echo and Log are local I/O, so the sum-of-trigger-durations latency cost is microseconds in practice. The v1 dispatcher has no per-attempt timeout (see Q6 amendment); a pathological filesystem hang during a single dispatch attempt would block shutdown until the OS call returns. Documented in the watch overview.

  - **Where trigger config lives (Q2)**: per-watch only, via `WatchRequest::with_triggers(Vec<Trigger>)`. No client-level default. Maps directly to CLI YAML per-listener triggers and Python dict-to-struct. Per-client default would force the YAML loader to invent grouping rules. Forward-compatible: per-client default can be added later as sugar without breaking per-watch (the reverse would be breaking).

  - **`watch_with_handler` relationship (Q3)**: complementary. The handler stays consumer-side; triggers stay supervisor-side. D19 preserved (both surfaces drain the same channel from the same supervisor task). Handler failure cancels the watch but does NOT roll back the commit; at-least-once for user closures requires either a future closure-trigger variant or configuring a Trigger explicitly. Documented limitation: triggers are for declarative durable side effects, the handler is for programmatic observation.

  - **Required vs optional semantics (Q4)**: ship both, default `required: true`. Required terminal failure terminates the watch with `ClientError::TriggerFailed { kind, source }`, commit stays at previous value, next process start re-delivers the same notification. Optional terminal failure WARN-and-continues with full error context; commit decision is unaffected. Per-trigger `required: bool` field with the safer default; users explicitly opt out to get loose semantics.

  - **Trigger dispatch order (Q5)**: sequential in declaration order. `for trigger in &triggers { dispatch(trigger).await }`. Required terminal failure short-circuits the loop and terminates the watch; optional terminal failure WARNs and continues to the next trigger. No `tokio::spawn`, no `CancellationToken` cascade across siblings, no parallel-ordering-nondeterminism in tests. Forward-compatible to add parallel later as a per-watch flag (`WatchRequest::with_triggers_parallel(bool)`) or a `TriggerSet { mode: Sequential | Parallel }` wrapper if a real use case appears.

  - **Per-trigger config shape (Q6)**: fields are {`retries: u32` (default 0; library-chosen exponential backoff via the supervisor's existing `compute_backoff`), `required: bool` (default true)}. `fail_fast` is dropped from v1 because Echo and Log have no retryable/non-retryable error distinction; it lands when the Webhook trigger appears. **`timeout` was also dropped from v1** after oracle plan review on the trigger PR surfaced two correctness issues: `tokio::time::timeout` cannot interrupt a synchronous `std::io::Write::write_all` call (no preemption point inside the sync future), and on async `tokio::fs::write_all` a hard cancellation mid-call produces a partial NDJSON line. The original Q6 rationale ("prevents pipeline stall on broken-pipe-style hang") was incorrect; broken-pipe surfaces as an immediate `io::Error`, not a hang. The v1 dispatcher runs each attempt to completion; local triggers complete in microseconds in practice. A `.timeout()` builder method will be added when the Webhook trigger ships, where `reqwest`'s HTTP-level timeout bounds it meaningfully. Public builder API: `Trigger::echo()`, `Trigger::log(path)`, `.retries(n)`, `.required(b)`. `#[non_exhaustive]` with private fields.

  - **Echo trigger output (Q7)**: writes compact NDJSON (one notification per line, trailing `\n`) to `io::stdout().lock()` via a single `write_all(&buf)` against a buffer built by `serde_json::to_vec` + `buf.push(b'\n')`. The buffer-then-write shape removes the intra-trigger JSON-body-vs-newline seam. No destination knob, no format knob. D12 governs diagnostic logs (which still go through `tracing`); Echo is the trigger's named data-output channel, not a log. Forward-compatible to add `with_target(EchoTarget)` later if a real tracing-routing use case appears. `println!` is not used (AGENTS.md); the explicit named write on a locked stdout handle is allowed because it is named data output, not a hidden log.

  - **Log trigger output (Q8)**: required path argument to `Trigger::log(path)` (no default; default would footgun surprise file creation). Open mode: append + create-if-missing. Write semantics: async via `tokio::fs::File` + `tokio::io::AsyncWriteExt::write_all`, with a buffer-then-write pattern (serialize the notification into `Vec<u8>` with the trailing `\n` appended to the same buffer, then a single `write_all(&buf)` call). The buffer-then-write shape removes the JSON/newline split inside this code path; it does NOT promise one syscall or arbitrarily-large multi-process append safety, since `write_all` may loop internally on short writes. No per-write `fsync` (at-least-once at the state-store level already covers crash replay; a crashed pre-commit log write replays on restart). Format: NDJSON same as Echo. No rotation (external tools like `logrotate`; the library does not detect renames, does not reopen on SIGHUP). File handle lifecycle: lazy-open on first dispatch, hold via the dispatcher's per-trigger state for the trigger lifetime, close via RAII on supervisor exit. Multi-listener to the same path opens independent FDs.

  - **Trigger cancellation on watch drop (Q9)**: hybrid. Within a single dispatch attempt (one `write_all` call): let-finish (the atomic unit, analogous to one `StateStore::put` call). Between retry attempts (backoff sleep): cancel via `select! { parent_cancel.changed() => exit }`. Between triggers in the per-notification loop: cancel via the same `select!`. Without a per-attempt timeout (Q6 amendment), the single-attempt completion time is bounded only by the OS: microseconds for local stdout/file writes, potentially longer on pathological filesystems (NFS hang, FIFO without reader). No partial-write risk under v1 (no NDJSON corruption from cancellation, because the buffer-then-write shape means the cancellation point is BETWEEN attempts, not mid-write). Re-delivery on restart preserves at-least-once.

  - **Commit timing under triggers (Q10)**: commit-on-next-send mechanism from PR-E2b is preserved unchanged. Pipeline: `triggers → send N → wait for pull → commit N when about to send N+1`. Capacity-1 channel (when a state store is configured) still enforces "pull N+1 implies N committed". At-least-once preserved for BOTH raw `watch()` Stream consumers AND triggers. There is NO checkpoint-policy swap; triggers slot in front of the existing send. The PR-E2b plan's "interim policy" framing was misleading; the right framing is "PR-E2b ships the commit mechanism; PR-F adds a pre-send gate that uses it". A commit-before-send alternative was considered and rejected because it loses at-least-once for raw `watch()` Stream consumers who do not configure triggers (a stream drop between commit and pull loses the notification from the consumer's view).

  - **Multi-listener aggregate (Q11)**: no aggregate API in PR-F. D20 preserved. The CLI daemon composes per-listener watches via a small `for + JoinSet` loop; Python composes via `asyncio.gather(*[client.watch(req) for req in reqs])`. Aggregate sugar (`watch_many`, `run_many`, or a merge-`Stream` `ListenerSet`) can land later if a demonstrated use case appears. The trigger work is per-watch (Q2) so it does not change the multi-listener calculus.

  - **PR-F scope split (Q12)**: single PR. Estimated ~900 LOC total: ~80 public `Trigger` builder, ~150 internal `TriggerKind` enum (with `#[cfg(test)]` `TestFailing` and `TestFailOnCall` variants for unit-test failure injection) + sequential dispatcher with retry-via-`compute_backoff` + hybrid parent_drop cancellation, ~40 Echo impl, ~70 Log impl, ~40 supervisor integration (one new dispatch step before existing `send_or_cancel`), ~20 `WatchRequest::with_triggers`, ~25 `ClientError::TriggerFailed` variant, ~250 unit tests (covering builder, formatter, dispatch, retry-via-TestFailing, cancel-during-backoff, success-after-retry, prev-committed-before-current-trigger-fails via TestFailOnCall), ~300 integration tests, ~80 docs. Echo and Log share the dispatcher infrastructure; splitting would duplicate test scaffolding without proportional review-quality gain. D11-complete at first merge (both Echo and Log present). Comparable in size to PR-E2b (~900 LOC, single PR shipped successfully through 12 Copilot rounds). Branch name `feat/triggers` (or similar). The 11-gate CI set (10 from PR-E2b plus a new `cargo doc -D warnings` gate) must be green on every commit. If during implementation Log turns out to be larger than estimated (e.g., complex `tokio::fs` error handling), splitting mid-stream is easier than merging two PRs after the fact.

- *Cross-process state-store hardening design*: resolved through four rounds of oracle plan review on the multi-process JSON file store. The decisions below fix the public-surface and internal architecture for the multi-process work.

  - **Lock crate (Q1)**: `fd-lock` v4.x (pinned `fd-lock = "4.0"` per AGENTS.md's minor-version pin rule). Picked over `fs2` because fd-lock is actively maintained (last commit 2025-04-23, three owners including the `rustix` and `windows-sys` authors), uses `rustix::fs::flock` on Unix and `LockFileEx` via `windows-sys` on Windows, and exposes an `RwLock<T>` wrapper with RAII guards that fits the read-modify-write pattern naturally. `fs2`'s last release was 2018-01-06 with a single owner; abandoning a load-bearing dependency to a stale crate is unacceptable. `fs4` (modern fork of fs2 with async support) was considered but rejected because async-native locking adds complexity without benefit; `spawn_blocking` around a sync lock is the idiomatic tokio pattern and lock hold time is sub-millisecond.

  - **Lock subject (Q2)**: a sidecar lockfile at `<state_path>.lock` (e.g., `~/.config/aviso/state.json.lock`). Locking the data file itself is unsafe in combination with our atomic-rename write pattern: `write_atomically` does temp-write + `rename(2)` over the target, which replaces the target path's inode. A `flock` held on the pre-rename inode persists on the now-unnamed old inode while the path itself points at a new, unlocked inode that a sibling process can immediately re-open and re-lock. SQLite avoids this because its main database file is updated in-place via WAL or rollback-journal patterns, not by atomic rename. Our crash-safety strategy is incompatible with locking the data file. The sidecar is never renamed, so the lock semantics remain stable across writes. Sibling placement keeps the lockfile on the same filesystem as the state file. The lockfile is created lazily on first `put` and never deleted by the library; documented in `JsonFileStore` rustdoc as a precondition that the user must not delete it (external deletion would let two writers acquire "the" lock on two different inodes).

  - **Lock granularity (Q3)**: one exclusive lock per `write_through` cycle, covering the entire read-modify-write window. Acquired inside `spawn_blocking`, released when the `RwLockWriteGuard` drops at end-of-scope. No per-key locking, no separate read locks. The JSON file is small (kilobytes in production), merge work is microseconds, contention is rare. Acquired blocking (`RwLock::write`), not non-blocking (`try_write`).

  - **Stale-lockfile detection (Q4)**: not needed. `flock(2)` and `LockFileEx` are automatically released when the holding process exits, including from `SIGKILL`. The kernel handles this at the syscall layer.

  - **Monotonic-cursor merge (Q5)**: three-rule merge inside the lock, after re-reading disk state. Takes `candidate` (in-memory map after the mutator ran), `disk_state` (re-read under the lock), and `deletes: HashMap<ResumeKey, u64>` (map from deleted keys to their pre-state sequence at delete time). Rules:
    1. Key in candidate AND disk's sequence > candidate's: disk wins (no backward motion).
    2. Key in disk but NOT in candidate AND NOT in deletes: preserve disk (other process's write).
    3. Key in deletes: if disk has it AND disk's sequence > pre-state sequence we recorded, delete suppressed, preserve disk (concurrent writer wins the "delete the K I knew" intent). Else honour the delete.
    The third rule fixes the original draft's bug where `DELETE K` against concurrent `PUT K=N+M` would silently drop the concurrent write.

  - **Cancel-safety (Q6)**: `put` and `delete` remain NOT cancellation-safe. The existing trait docstring already warned that dropping the future after `spawn_blocking` starts the disk write but before the in-memory install completes causes disk-and-memory divergence. The new lock + merge widens that window: lock-acquire latency (potentially unbounded if a sibling holds the lock) is added between spawn_blocking start and disk-write start. A dropped future means the in-memory install never runs; subsequent `get` calls on this handle return stale data until the handle is dropped and re-opened. Callers must drive `put`/`delete` to completion and must not `select!` them against cancellable arms.

  - **`EINTR` retry (Q7)**: `rw_lock.write()` can return `io::ErrorKind::Interrupted` if the underlying `flock` syscall is interrupted by a signal. Wrap acquisition in a small `loop { match ... Interrupted => continue ... }` and surface non-Interrupted errors as `StoreError::Io`. `std::fs::OpenOptions::open` already handles EINTR internally on Unix; the retry is only needed around the `flock` call.

  - **Fuzz harness (Q8)**: `crates/aviso/tests/state_store_kill_fuzz.rs` with `harness = false` so the test file has its own `fn main()`. Self-spawning: the same compiled artifact acts as parent (cargo test invocation) or as fuzz writer (when the magic argv `--fuzz-writer-mode` AND env var `AVISO_FUZZ_CHILD=1` are both set). Uses `args_os` for non-UTF-8 path safety. Parent spawns N=4 children for 500 ms, kills them via portable `Child::kill()` (SIGKILL on Unix, TerminateProcess on Windows). Per-child append-only journal files record successfully-committed sequences. Assertion: after `JsonFileStore::open` on the survived file, for each child's key, `stored_sequence >= max(journaled_sequences_for_that_child)`. Second wave with starting sequence 0 verifies no cross-wave backward motion. Portable across Linux and macOS now; Windows when the wheel matrix lands.

  - **`client.resume.applied` INFO log (Q9)**: emitted by the supervisor at the `Ok(Some(cp))` branch of the initial-cursor `match` in `run_supervisor`. Fields: `event.name = "client.resume.applied"`, `resume_key = %resume_key.as_hex()`, `sequence = cp.last_committed_sequence`, `event_id = cp.last_event_id.as_deref()`. INFO level per D2. The no-checkpoint-found path stays silent (starting fresh is the default; INFO there would be noise).

  - **API surface delta (Q10)**: zero new public types, zero new builder methods, zero new `StoreError` variants. The only user-visible changes are the `JsonFileStore` rustdoc update ("multi-process safe for cooperating processes on local filesystems" plus sidecar-lockfile + no-external-delete + widened cancel-safety constraints) and the D4 ADR amendment.

  - **Workspace dep (Q11)**: `fd-lock = "4.0"` added to `[workspace.dependencies]`. Only crate `aviso` consumes it. License MIT-OR-Apache-2.0, dual; already on the deny.toml allowlist.

  - **PR scope (Q12)**: single PR, five commits. Branch name `feat/state-store-multi-process`. Estimated ~700 LOC total: ~30 dep + manifest, ~250 lock + merge in `file.rs` (with the EINTR retry, the `deletes` map computation, and the merge helper), ~300 fuzz harness, ~40 supervisor INFO log + test, ~30 D4 ADR amendment, ~50 rustdoc updates. Each commit independently passes the 11-gate set + em-dash + banned-words sweeps.

- *Phase 4 trigger expansion design*: settled before implementation. The decisions below fix the public-surface and internal architecture for the `command` and `webhook` trigger kinds, the template engine they share, and the YAML deserialiser. Designed fresh for the Rust client; we read pyaviso for use cases (operators shell out, ops teams post to Slack/Teams/Discord) but do not bind ourselves to its API shape. The existing `echo`/`log` dispatcher infrastructure from PR-F is reused unchanged.

  - **Trigger surface (T1)**: two new kinds. `Trigger::command(cmd: impl Into<String>)` spawns a child process. `Trigger::webhook(url: impl Into<String>)` POSTs to an HTTP endpoint. Both flow through the existing `TriggerKind` internal enum (new variants `Command { ... }` and `Webhook { ... }`); both flow through the existing dispatcher loop (sequential, retry via `compute_backoff`, hybrid cancellation per Q9). No new public trait; the `#[non_exhaustive]` enum stays the extension point.

  - **Template engine (T2)**: small in-crate engine at `crates/aviso/src/watch/trigger/template.rs`, ~80 LOC. Syntax: `{{ notification.<dotted.path> }}` substitutes a field from the notification JSON (resolves nested objects via `serde_json::Value::pointer`); `{{ env.<NAME> }}` substitutes from the process environment. Literal `{{` is escaped as `\{{`. Missing `notification.<path>` is a typed `TriggerError::Template { template, field, kind: Missing }` error; missing env var is `TriggerError::Template { ..., kind: EnvNotSet }`; non-string value (e.g., substituting an object into a string position) is `TriggerError::Template { ..., kind: NotString }`. Engine compiles a template once at `Trigger` builder time and reuses across dispatches; errors surface at first dispatch, not at build time, because env-var changes between builds are valid. Tested via property tests on the parse + substitute round-trip and targeted regressions for each error kind. No new workspace dep.

  - **Command trigger semantics (T3)**: spawn `tokio::process::Command::new("/bin/sh").arg("-c").arg(cmd_template_substituted)` on POSIX. Stdin inherited (the child can read interactively; in practice it is closed). Stdout and stderr captured to ring buffers (4 KiB each); stdout is logged at DEBUG, stderr at WARN on success and included in the error on failure. Environment variables: the dispatcher injects `AVISO_NOTIFICATION_ID`, `AVISO_NOTIFICATION_TYPE`, `AVISO_NOTIFICATION_SOURCE`, `AVISO_NOTIFICATION_TIME`, `AVISO_NOTIFICATION_JSON` (the full notification as compact JSON), plus `AVISO_IDENTIFIER_<KEY>` for each key in `data.identifier` (uppercased, non-alphanumeric replaced with `_`), and `AVISO_PAYLOAD_<KEY>` for each key in `data.payload`. User-set `env:` entries override (last-write-wins, dispatcher-injected first). `command:` string is the only place template substitution applies in v1; `env:` values are taken literally (templating env values is a follow-up if a real use case appears). Working directory: `working_dir` value if set, otherwise the process's current directory; if the set path does not exist or is not a directory, `TriggerError::Command { exit_code: -1, stderr_tail: "<working_dir error>" }`. Timeout: `tokio::time::timeout(t, child.wait_with_output())`; on expiry, `child.kill().await` and surface `TriggerError::Timeout(t)`. Windows: deferred to the wheel matrix phase; v1 documents POSIX-only in rustdoc and runs `compile_error!` if `cfg(windows)` to fail at compile time on a Windows build.

  - **Webhook trigger semantics (T4)**: built on the supervisor's existing `reqwest::Client` (so TLS knobs from the CLI propagate automatically). `Trigger::webhook(url)` takes the URL with template substitution applied at dispatch time. Default method `POST`; `.method(HttpMethod)` overrides to `GET`/`PUT`/`PATCH`/`DELETE` (the four likely-needed verbs; `HEAD`/`OPTIONS` deferred until asked). Headers via `.header(k, v)` (repeatable; templated values resolved at dispatch); default `Content-Type: application/json` injected if no `Content-Type` header is set by the user. Body: `body_template` if set (template-substituted), otherwise the full notification as compact JSON (same shape `echo` emits). Timeout: `Request::timeout(t)` from `reqwest`; default 30s. Retry classifier: a response is "retryable" if status is 5xx OR if the request errored at the transport layer (DNS/TCP/TLS); 4xx is "terminal" when `fail_fast = true` (the default). `fail_fast = false` retries every error including 4xx; useful for an unreliable receiver where 4xx is transient. Error: `TriggerError::Webhook { status: Option<StatusCode>, body_tail: String }`; `status` is `None` for transport errors. Response body captured to last 4 KiB; full body is dropped (Slack/Teams/Discord all return short responses anyway). No connection pool tuning; reqwest's default pool is fine for the per-watch dispatch rate (~1 req per notification, single-digit per second at peak).

  - **`Trigger::timeout` and `fail_fast` resurrection (T5)**: the deferred v1 fields land. `.timeout(Duration)` is meaningful for `command` (tokio's `Child::kill().await` interrupts cleanly) and `webhook` (`reqwest`'s `Request::timeout` interrupts cleanly); it is silently ignored for `echo` and `log` because their dispatchers complete in microseconds and the rationale for dropping it in v1 (sync `write_all` is not preemptible) still holds. `.fail_fast(bool)` is meaningful for `webhook` (4xx terminal vs retryable) and `command` (terminal on non-zero exit when `true`; retryable when `false`); silently ignored for `echo` and `log`. The "silently ignored on echo/log" choice avoids a `TriggerKind`-specific builder hierarchy; documented in the rustdoc.

  - **`TriggerError` expansion (T6)**: three new variants under `#[non_exhaustive]`: `Command { exit_code: i32, stderr_tail: String }`, `Webhook { status: Option<reqwest::StatusCode>, body_tail: String }`, `Template { template: String, field: String, kind: TemplateErrorKind }` where `TemplateErrorKind` is an inner enum (`Missing`, `EnvNotSet`, `NotString`). `Timeout(Duration)` was already reserved in v1's `#[non_exhaustive]` enum and now ships. The `TriggerKindLabel` diagnostic enum gains `Command { command_summary: String }` and `Webhook { url_host: String }` variants (the labels include redacted summaries so error logs are useful without leaking secrets; the full `command:` string and full `url` stay in the dispatcher's debug-level structured fields).

  - **YAML trigger config (T7)**: serde-derived `TriggerConfig` enum at `crates/aviso/src/watch/trigger/yaml.rs`. Tagged on `type`; one variant per `TriggerKind`. Each variant carries its body in a named payload struct (not inline-struct variants) so `#[serde(deny_unknown_fields)]` on the struct catches misspelled keys within a matched variant; the outer-enum form does not catch them per serde-rs issue #2123. Updated shape:
    ```rust
    #[derive(serde::Deserialize)]
    #[serde(tag = "type", rename_all = "snake_case")]
    #[non_exhaustive]
    pub enum TriggerConfig {
        Echo(EchoConfig),
        Log(LogConfig),
        #[cfg(unix)]
        Command(CommandTriggerConfig),
        Webhook(WebhookTriggerConfig),
    }
    #[non_exhaustive]
    #[derive(serde::Deserialize)]
    #[serde(deny_unknown_fields)]
    pub struct EchoConfig { #[serde(default)] retries: u32, #[serde(default = "default_required")] required: bool }
    #[non_exhaustive]
    #[derive(serde::Deserialize)]
    #[serde(deny_unknown_fields)]
    pub struct LogConfig { path: PathBuf, #[serde(default)] retries: u32, #[serde(default = "default_required")] required: bool }
    // CommandTriggerConfig and WebhookTriggerConfig follow the same pattern with their full field set.
    impl TriggerConfig { pub fn into_trigger(self) -> Trigger { ... } }
    ```

- *Phase 4 email trigger direction*: settled before implementation; granular Q&A deferred to PR-G3 branch-plan time. The decisions below fix the high-level direction so PR-G2 (webhook) and PR-G3 (email) can be sequenced without further design churn.

  - **Backend (E1)**: direct SMTP via the `lettre` crate. lettre is the de-facto Rust SMTP client (Apache-2.0 / MIT dual, actively maintained, ~10M downloads), supports plain SMTP, STARTTLS, implicit TLS, PLAIN/LOGIN auth, with rustls (no openssl dep, no system C deps). Cross-platform: the email trigger works on Windows too (unlike `command` which is `#[cfg(unix)]`-gated). Excluded: proprietary HTTP delivery APIs (AWS SES, SendGrid, Mailgun) per §7.2 no-managed-services stance. Excluded: spawning a local `sendmail`/`msmtp` binary (operators who want the local-MTA recipe already have the `command` trigger; we don't need a second path for that).

  - **SMTP destination model (E2)**: operator-configured. Per-trigger YAML carries `smtp_host`, `smtp_port`, `smtp_user`, `smtp_password`, `tls_mode` (`Implicit` for port 465, `StartTls` for port 587, `None` for unencrypted local relays), `from`, `to`, optional `cc`/`bcc`, templated `subject`, templated `body`. Operators point it at Gmail (smtp.gmail.com:587 + STARTTLS + app password), Outlook / Office365 (smtp-mail.outlook.com:587 or smtp.office365.com:587), ProtonMail Bridge (localhost:1025 + StartTls + bridge credentials), the operator's own Postfix relay, or any RFC-5321 server. Credentials in YAML use the existing template engine's `{{ env.<NAME> }}` substitution so secrets live in env vars not config files.

  - **Public surface (E3)**: `Trigger::email(EmailConfig)` constructor (taking a config struct rather than a long builder chain because the config has ~9 fields and the struct shape maps directly to YAML); standard `.retries`, `.required`, `.timeout`, `.fail_fast` tunables (all four already on the parent `Trigger` since PR-G1); cross-platform (no `#[cfg(unix)]` gate). Public `TriggerError::Email { kind: EmailErrorKind, message: String }` variant with `EmailErrorKind` enum (`SmtpConnect`, `SmtpAuth`, `SmtpDelivery`, `MalformedAddress`, others as the engine surfaces them) under `#[non_exhaustive]`. Public `TriggerKindLabel::Email` unit variant (cross-platform; no body so secret-bearing SMTP host or recipient addresses cannot leak through the public error chain). Template-substitution failures in subject/body/headers/credentials reuse the existing `TriggerError::Template` variant from PR-G1 with `context = "email subject"`, `"email body"`, `"email header"`, `"email credentials"` etc.

  - **Retry classifier (E4)**: `SmtpConnect` and `SmtpDelivery` with a transient SMTP 4xx code are retryable. `SmtpAuth`, `MalformedAddress`, and `SmtpDelivery` with a permanent SMTP 5xx code are terminal under `fail_fast = true` (the existing dispatcher default). The classifier extension lands in PR-G3 by adding the new variants to the existing `is_terminal_error` match.

  - **PR sequencing (E5)**: email lands as PR-G3, AFTER PR-G2 (webhook). Rationale: webhook design is already locked in (§5 Resolved Phase 4 trigger expansion), webhook ships the YAML deserialiser scaffolding that email reuses, and webhook is the smaller-and-faster ship (no new crate dep; reuses the existing `reqwest::Client`). Email adds the `lettre` workspace dep and an SMTP integration-test harness, both heavier than webhook's footprint.

  - **Out of scope for PR-G3 v1 (E6)**: HTML email (text-only bodies in v1; HTML lands when a real use case appears). Attachments. DKIM signing (let the SMTP server handle it). Bounce processing / DSN handling. Connection pooling across multiple notifications (one connection per dispatch attempt; SMTP isn't a hot path for this client's workload). OAuth2 / XOAUTH2 (password-only in v1; OAuth lands when an operator with Office365 modern-auth needs it). Multiple `to` recipients per send IS in scope; CC and BCC are also in scope; multipart/alternative is not.

- *Phase 5 CLI design*: settled before implementation. The decisions below fix the public-surface (the `aviso` binary's command tree, flags, environment variables, file paths, output format, exit codes) and internal architecture (clap structure, config layering, auth construction, shutdown handling, testing strategy) for the CLI work. The CLI scaffold already exists at `crates/aviso-cli/src/main.rs` (47 LOC: clap derive `Cli` skeleton, anyhow main, JSON tracing-subscriber to stderr per D12 with `AVISO_LOG` `EnvFilter`, startup `tracing::info!` event); the CLI phase expands it. YAML trigger configuration (per-listener `triggers:` list) is in scope per the Phase 4 trigger expansion that lands first.

  - **clap framework (Q1)**: clap derive (matches existing scaffold). Top-level `Cli` struct with global flags (`--config`, `--state-file`, `--base-url`, `--token`, `--ca-bundle`, `--danger-accept-invalid-certs`, `--json`, `--no-color`, `--verbose/-v`, `--yes`) plus a `command: Commands` subcommand enum. clap auto-generates `--help` and `--version` (the latter sourced from `aviso::VERSION` already exposed by the lib).

  - **Subcommand surface (Q2)**: nine top-level subcommands, mirroring the §3 Phase 5 plan plus one addition for completions:
    - `aviso notify --event-type <T> --identifier <K=V>... --payload <JSON|@file|-> [--metadata <K=V>...]`: POST one notification. `--payload @file` reads from a path; `--payload -` reads from stdin.
    - `aviso watch <EVENT_TYPE> [--filter <JSON>] [--from-id <N> | --from-date <STR>] [--no-state-store]`: stream notifications. Output is NDJSON on stdout regardless of TTY (because the stream is long-running and downstream consumers pipe it). State store defaults to `~/.config/aviso/state.json`; `--no-state-store` opts out and uses `MemoryStore` (good for one-shot tests).
    - `aviso replay <EVENT_TYPE> [--filter <JSON>] (--from-id <N> | --from-date <STR>)`: stream the historical replay only. Same NDJSON output. `--from-id` or `--from-date` is required (the replay endpoint requires a resume point).
    - `aviso schema list`: GET `/api/v1/schema`. Output: human-readable table (TTY) or NDJSON (pipe), one schema descriptor per row.
    - `aviso schema get <EVENT_TYPE>`: GET `/api/v1/schema/{event_type}`. Output: JSON (always; schemas are JSON documents).
    - `aviso admin wipe-stream <EVENT_TYPE> --yes`: DELETE `/api/v1/admin/wipe/stream`. `--yes` required.
    - `aviso admin wipe-all --yes`: DELETE `/api/v1/admin/wipe/all`. `--yes` required.
    - `aviso admin delete <NOTIFICATION_ID> --yes`: DELETE `/api/v1/admin/notification/{id}`. `--yes` required.
    - `aviso auth check`: GET `/health` with the resolved auth header attached; report whether the credentials work and which auth source they came from.
    - `aviso config dump [--redact]`: print the resolved config (flag-overrides applied on top of env-overrides applied on top of file-defaults). `--redact` masks passwords/tokens.
    - `aviso completions <SHELL>`: print shell completions for bash, zsh, fish, powershell, or elvish, using `clap_complete`.

  - **Config file format and layering (Q3)**: YAML via `serde_norway` (already in workspace deps). File schema:
    ```yaml
    base_url: "https://aviso.example.org"
    auth:
      bearer_token: "..."          # OR
      basic:
        username: "alice"
        password: "..."
    timeout_seconds: 30
    heartbeat_interval_seconds: 30
    state_file: "/path/to/state.json"
    ```
    Precedence per field: explicit CLI flag > `AVISO_*` env var > config file > built-in default. Layering is per-field, not whole-config replacement (a flag override of `--base-url` does not blank out a file-set `auth.bearer_token`). The resolved config is materialised into an `AvisoClientBuilder` per invocation.

  - **Default paths and overrides (Q4)**: config file `~/.config/aviso/config.yaml`, state file `~/.config/aviso/state.json`. `~` resolves via `directories` crate (new workspace dep) for cross-platform parity (uses `$XDG_CONFIG_HOME` on Linux, `~/Library/Application Support` on macOS, `%APPDATA%\aviso` on Windows; we deliberately override macOS and Windows to `~/.config/aviso` for the simpler per-user layout the user requested). Flag overrides: `--config <path>`, `--state-file <path>`. Env overrides: `AVISO_CLIENT_CONFIG_FILE`, `AVISO_STATE_FILE`. Default-creation policy: the parent directory is created on first run if absent (`std::fs::create_dir_all` with `0700` perms on Unix); the config file is NOT created (missing file uses built-in defaults); the state file is created lazily on first `put` by `JsonFileStore` itself.

  - **Output format (Q5)**: human-readable text for TTY stdout, NDJSON for non-TTY (pipe, file redirect). TTY detection via `std::io::IsTerminal` (no new dep; stabilised in 1.70). `--json` forces JSON regardless of TTY. `--no-color` disables ANSI colour codes (useful in non-TTY where `--json` would have been forced and we want plain text). `watch` and `replay` always emit NDJSON (because they're long streams that downstream consumers pipe); other commands respect the TTY/format flags.

  - **Error reporting and exit codes (Q6)**: `anyhow::Result<()>` from main with `.context(...)` at every layer transition per AGENTS.md "Binaries: anyhow::Result is fine. Add .context(\"doing X\") at every layer transition so failure messages tell a story." Exit codes: `0` success, `1` runtime error (server returned 4xx/5xx, network failure, file I/O failure), `2` usage error (missing required flag, invalid argument, destructive command without `--yes`). Unhandled `ClientError` variants flatten to exit 1 with the error chain printed to stderr.

  - **Logging (Q7)**: already shipped per the existing scaffold. `tracing_subscriber::fmt::json()` to stderr with `AVISO_LOG` `EnvFilter` (default `INFO`). The `--verbose/-v` flag bumps to DEBUG (and `-vv` to TRACE) regardless of `AVISO_LOG`. The `init_tracing` helper at `crates/aviso-cli/src/main.rs:14-33` is the canonical entry point; subcommand handlers `tracing::info!` at meaningful boundaries (request start, response received, fatal error). Notification payloads are NOT logged by default per D12's redaction-at-emission rule; `--verbose` does not enable payload logging (it stays off; a future `--log-payloads` flag could opt in if a user needs it for debugging).

  - **Authentication source layering (Q8)**: build an `AuthProvider::Chain` of `ConfigFileAuth` (lowest priority) + `EnvAuth` (`AVISO_TOKEN`, `AVISO_USERNAME`, `AVISO_PASSWORD`) + explicit CLI flags (`--token`, `--username`, `--password`; highest priority). The chain is constructed in `crates/aviso-cli/src/auth.rs` (new file) and passed to `AvisoClientBuilder::auth()`. Explicit `--token` and explicit `--username/--password` are mutually exclusive (clap `conflicts_with`); the error message names both.

  - **Destructive confirmation (Q9)**: `--yes` (or `-y`) required for `admin wipe-stream`, `admin wipe-all`, `admin delete`. Without `--yes`, the command exits 2 (usage) with a stderr message naming the flag. No interactive prompt; aviso runs in CI and batch jobs where stdin is unavailable or non-interactive. The `--yes` flag is per-invocation, not global; cannot be set in the config file (a config file `--yes` would defeat the protection).

  - **TLS dev knobs (Q10)**: `--ca-bundle <PATH>` accepts a PEM-encoded bundle of additional root certificates; passed to `reqwest::ClientBuilder::add_root_certificate` for each cert. Useful for self-hosted aviso-server with an internal CA. `--danger-accept-invalid-certs` toggles `reqwest::ClientBuilder::danger_accept_invalid_certs(true)`. The latter emits a `tracing::warn!` event `event.name = "cli.tls.insecure_mode"` on every request (not just startup) so log scrapers can detect prolonged misuse. Both flags are global; both can be set in the config file (`tls.ca_bundle`, `tls.danger_accept_invalid_certs`).

  - **Graceful shutdown (Q11)**: install Ctrl+C handler via `tokio::signal::ctrl_c().await` running on a dedicated task that flips a `tokio::sync::watch::Sender<bool>` cancellation token shared with subcommand handlers. `watch` and `replay` subcommands `select!` on `cancel.changed()` alongside `stream.next()` and drop the `NotificationStream` cleanly (which triggers the supervisor's existing cancel cascade per D19 / D20). First Ctrl+C: graceful shutdown, drain in-flight commit + flush stdout, exit 0. Second Ctrl+C within 5 seconds: hard exit via `std::process::exit(130)` (128 + SIGINT). The 5-second window is intentional: it gives the supervisor time to land a pending state-store commit but bounds the operator's wait if something is stuck.

  - **Shell completions (Q12)**: `clap_complete = "4.5"` (new workspace dep; matches the existing clap pin). The `aviso completions <SHELL>` subcommand writes the appropriate script to stdout. Supports `bash`, `zsh`, `fish`, `powershell`, `elvish` (clap_complete's full set). Installation instructions go in the user-facing docs (`docs/src/usage/cli.md`); do NOT auto-install (the CLI doesn't have permission to write to system locations and would surprise users).

  - **Testing strategy (Q13)**: integration tests via `assert_cmd = "2.0"` and `predicates = "3.1"` (both new dev-deps). Tests live at `crates/aviso-cli/tests/`. Coverage: one happy-path test per subcommand against a `wiremock`-backed mock server (already a workspace dep); a few error-path tests (`admin wipe-all` without `--yes` exits 2; `notify` with bad JSON exits 2 with the validation error in stderr; `watch` with `--no-state-store` does not touch the default `state.json`). - *Phase 5 CLI granular settlement*: settled via a discussion-first design walk after PR-G2 merged, before the `feat/cli` branch plan was written. The amendments below override the locked Q1-Q18 design where they conflict; the rest of Q1-Q18 stands unchanged. References to "pyaviso" cite the project at `https://github.com/ecmwf/aviso` at commit `1a17a18` as researched during the design walk.

  - **Amendment A (subcommand rename: `watch` -> `listen`)**: the `aviso watch` subcommand is renamed to `aviso listen` to match pyaviso's surface. Library-level names stay unchanged (`AvisoClient::watch()`, `WatchRequest`, `NotificationStream`); only the CLI subcommand renames. The `replay` subcommand keeps its name (pyaviso uses the same `--from` / `--to` knobs on `listen`; we keep them as a separate subcommand per Q2).

  - **Amendment B (listener-list YAML config shape, pyaviso-compatible)**: the YAML config schema gains a top-level `listeners:` list that mirrors pyaviso's listener model, with two divergences. (1) `request` is renamed to `identifiers` (matches the Rust API's `Notification::identifier` field). (2) The existing `{{ notification.<path> }}` / `{{ env.<NAME> }}` template syntax shipped in PR-G1 is preserved; we do NOT migrate to pyaviso's `${request.xxx}` / `${json}` / `${jsonpath}` syntax. Each listener carries an optional `name:` field (free string; lets `aviso replay --listener <NAME>` pick one entry), a required `event:` field (the event_type stream), an optional `identifiers:` mapping (server-side narrowing predicate; values may be scalars or arrays), optional `from_id` / `from_date` bootstrap fields, and an optional `triggers:` list (consumed via the existing `TriggerConfig::into_trigger` from PR-G2, so all four shipped trigger kinds are available from YAML). Example global config with listeners:
    ```yaml
    base_url: "https://aviso.example.org"
    auth:
      bearer_token: "..."

    listeners:
      - name: mars-od-fc
        event: mars
        identifiers:
          class: od
          stream: oper
          type: fc
        triggers:
          - type: log
            path: /var/log/aviso/mars-od.log
          - type: webhook
            url: "https://hooks.example.org/notify"
            headers:
              Authorization: "Bearer {{ env.HOOK_TOKEN }}"

      - name: era5-monthly
        event: era5
        identifiers:
          class: ea
        triggers:
          - type: command
            command: "./process.sh {{ notification.identifier.date }}"
    ```
    Pyaviso-compatibility note: pyaviso runs triggers in parallel; our dispatcher runs them sequentially per PR-F Q5 (the existing in-order semantic of `dispatch_triggers`). This is an intentional divergence; the user-facing `docs/src/usage/cli.md` documents it.

  - **Amendment C (positional listener files; `aviso listen [LISTENER_FILE...]`)**: `aviso listen` accepts a variadic positional list of listener YAML file paths.   - **Amendment H (drop `--to`; `--from <VALUE>` with lenient multi-format parse)**: pyaviso's `listen` subcommand has both `--from <DATE>` and `--to <DATE>`. Pyaviso's `--from` accepts ONLY a UTC date string in `YYYY-MM-DDTHH:MM:SS.ffffffZ` format (cli_aviso.py:218-222 at pyaviso commit 1a17a18 uses `click.DateTime(formats=["%Y-%m-%dT%H:%M:%S.%fZ"])`); pyaviso has no sequence-id support and the format is verbose (27 characters with full punctuation). So our CLI drops `--to` from the v1 surface. Operators who want a date-bounded window achieve it via shell pipelines (`aviso listen | jq 'select(.time < "2024-12-31")'`) or via a trigger that exits the process on a condition.

    Our `--from <VALUE>` is a SINGLE flag that accepts SEVEN forms, tried in this order:
    1. Pure-digit string parsed as `u64` -> routed as `from_id`. Examples: `42`, `1234567`.
    2. `YYYY-MM-DD` -> `from_date`, normalised to midnight UTC. Example: `2024-01-15`.
    3. `YYYY-MM-DD HH:MM` (space separator, hours+minutes) -> `from_date`, UTC. Example: `2024-01-15 14:30`.
    4. `YYYY-MM-DD HH:MM:SS` (space separator, full time) -> `from_date`, UTC. Example: `2024-01-15 14:30:00`.
    5. `YYYY-MM-DDTHH:MM:SS` (T separator, no Z) -> `from_date`, UTC. Example: `2024-01-15T14:30:00`.
    6. `YYYY-MM-DDTHH:MM:SSZ` (T separator, explicit UTC) -> `from_date`. Example: `2024-01-15T14:30:00Z`.
    7. `YYYY-MM-DDTHH:MM:SS.ffffffZ` (pyaviso strict, fractional seconds + Z) -> `from_date`. Example: `2024-01-15T14:30:00.000000Z`. Pyaviso parity for operators who copy date strings from pyaviso scripts.

    **Ambiguity resolution**: pure-digit input is ALWAYS routed as `from_id`. The compact YYYYMMDD form (`20240115`) is therefore NOT supported as a date even though it's common in ECMWF tooling; an operator who wants 15 Jan 2024 must use dashes (`2024-01-15`). The trade-off is clarity: a conditional rule like "8 digits is date, other lengths are id" would be conditional and harder to document. The user direction here is "writing a date should be easy"; dashes-plus-simple-time meets that bar without ambiguity.

    Internally, the CLI parses any of the seven forms via a try-each chain (the first form is `parse::<u64>().ok()`; the next six use the `chrono` crate's `NaiveDateTime::parse_from_str` with per-format format strings), then normalises the parsed datetime to a single wire format (`YYYY-MM-DDTHH:MM:SS.ffffffZ`, the pyaviso server contract) before constructing `ResumeStart::Date(String)`. The integer path constructs `ResumeStart::AfterSequence(n)` directly.

    Workspace dep delta: `chrono = "0.4"` added at the workspace level and to `crates/aviso-cli/Cargo.toml`. The library crate (`aviso`) gets no chrono dep; the library treats `from_date` as an opaque string and the SERVER does the date interpretation. If the user passes `--from foo` where `foo` is neither a u64 nor any of the six date forms, the CLI errors with the resolved value and lists the accepted forms in the stderr message (Error UX discipline applies).

### 7.2 Standing rules (verbatim, never override)

- "Don't ever merge without my approval" / "never ever merge without asking" / "please dont ever merge until I confirm". Unconditional. No agent system directive overrides this. The PR workflow always stops at the merge gate, even when oracle has issued PROCEED-TO-MERGE and CI is green.
- "Do not consider backwards compatibility when changing the implementation, this is an unreleased package." Drives the willingness to do breaking changes (e.g., dropping `.timeout()` from the trigger builder mid-design after the rationale failed).
- "NEVER DO THINGS LIKE V2 etc. remember this is not used anywhere, we just start yesterday, dont over engineer." Lock against speculative abstractions.
- "Always reply and resolve in the pr" for code-review comments: every Copilot comment gets a reply on the same thread naming the fix commit hash, then the thread is closed via the GraphQL `resolveReviewThread` mutation.
- "I dont see the PR, please in the pr message don't mention things like phases, oracle etc." applies to PR bodies AND commit messages AND code. Phase numbers, PR letters, "oracle", and "pass N" are banned everywhere except in `plans/`.
- Plan-only commits to `main` (changes only under `plans/`) MAY be pushed directly. Source-code commits MUST go through a PR.
- Never add `Co-authored-by:` trailers to commit messages.
- "I want this to be run in both python and c++ easily" informs every API shape decision; the Rust core stays neutral and binding-friendly (`Send + Sync + Clone` on `AvisoClient`, single `mpsc` channel per watch, no closure-heavy public surfaces unless absolutely needed).
- "I don't want sqlite, it is overengineering". The state store is JSON-file (`JsonFileStore`) plus `MemoryStore` for tests. No database backends.
- "Just lets make it ~/.config/aviso for the location of the config and the state". One directory for both; CLI defaults `config.yaml` and `state.json` live there.
- "no aws etc. please, we won't use managed services" + "people should be able to configure their servers like outlook, gmail etc." Excludes proprietary HTTP delivery APIs (AWS SES, SendGrid, Mailgun, similar) and any hard dependency on cloud-vendor SDKs. Operator-configured generic protocols are fine: SMTP for email (Gmail, Outlook, Office365, ProtonMail Bridge, a self-hosted Postfix, any RFC-5321 SMTP relay), HTTP for webhook (Slack incoming webhook, Teams workflow, Discord webhook, a self-hosted receiver). The user supplies the endpoint and credentials; aviso ships only the generic-protocol client. Future trigger / state-store / auth design choices must respect this stance.

### 7.5 The PR workflow (recipe)

The discipline that produced the resilience PR (#9) and the trigger PR (#10) cleanly:

1. **Discussion-first for design**: when a PR introduces meaningful design decisions, walk the user through them one question at a time, presenting two or three options each with a recommendation and trade-offs. Record every resolved decision in `plans/v0.3.md` §5 Resolved before drafting any code or branch plan. Single-question-at-a-time prevents the user being asked to context-switch across multiple unrelated knobs.

2. **Branch plan in scratch**: draft a comprehensive branch plan under `/var/folders/lt/jy_y3x896d1bs81999jkdhb40000gn/T/opencode/` (or wherever the temp scratch dir lives on the current machine). Cover: goal, out-of-scope, public surface, internal architecture, supervisor integration points by line number, error handling, test plan (unit + integration), docs delta, file touch list, commit plan (one concern per commit, ordered to keep every commit warning-clean), CI gates per commit, quality pass plan, risks, definition of done.

3. **Oracle plan review until PROCEED**: dispatch `oracle` subagent (via the `Task` tool with `subagent_type="oracle"`) with the scratch plan path plus relevant context (project `plans/v0.3.md`, `AGENTS.md`, `decisions.md`). Iterate by amending the plan and re-submitting against the same `task_id` for round-to-round continuity. The trigger PR took 8 rounds; the resilience PR took 6. Each round resolves explicit blockers; do not start coding until the round closes with one-line "PROCEED".

4. **Branch + implement in tight commits**: create the feature branch (`feat/<topic>`). Implement commits in the order the branch plan specifies. Each commit must pass all 11 CI gates locally before push. Use one concern per commit; if a hunk drifts into a second concern, split with `git add -p` and stash the rest. Never push a commit that has not passed the local gate set.

5. **Three quality passes**: after the last implementation commit, walk the diff three times before submitting to oracle. Pass 1 correctness (every `Result`, every `select!` arm, every `pending_commit` mutation, every cancel-safety claim, the buffer-then-write atomicity for I/O dispatchers, no new workspace deps that were not in the plan). Pass 2 API + docs (`#[non_exhaustive]` and `#[must_use]` on every new public surface, `missing_docs = "warn"` clean, intra-doc links resolve, mdbook code blocks compile). Pass 3 test + review-readiness (every integration test has a scenario sentence, every `expect` has a descriptive message, em-dash and banned-words sweep clean across the diff, all 11 CI gates green).

6. **Oracle code review until PROCEED-TO-MERGE**: dispatch oracle on the branch with a structured request for verdict (PROCEED-TO-MERGE / AMEND / REJECT). Provide commit list, files touched, branch plan path, ADR references, and explicit "what I want you to check" bullets. Iterate on rounds against the same `task_id`. Amend commits (interactive rebase + `git commit --amend`) when oracle flags per-commit issues; the goal is every commit on `main` independently passes the 11-gate set.

7. **Open PR with phase-/oracle-clean body**: `gh pr create --base main --head feat/<topic> --title '<conventional>' --body-file <scratch>`. The body MUST NOT contain "PR-[A-Z]", "Phase [0-9]", "oracle", "pass [0-9]" tokens. Verify with the banned-words sweep before submitting.

8. **Request Copilot review and drive rounds to completion**: request review via GraphQL: `gh api graphql -f query='mutation($pr:ID!,$bots:[ID!]!){ requestReviews(input:{pullRequestId:$pr,botIds:$bots}){ pullRequest{ number } } }' -f "pr=<pr_node_id>" -F "bots[]=<bot_node_id>"`. The bot login on this repo's reviews is `copilot-pull-request-reviewer[bot]`; the `botIds` reachable via `gh api graphql` are `copilot-swe-agent` (`BOT_kgDOC9w8XQ`), `anthropic-code-agent`, and `openai-code-agent`. In practice the user triggers Copilot from the PR UI ("Request reviewers" then pick Copilot) because the App-bot review path is not reachable from the GraphQL `requestReviews` mutation on this repo. ### 7.7 The comment-hook discipline (priority #3)

The repo's local hook fires on every docstring or block-comment edit and asks for one of four priorities. The rule that matters: priority #3 is "necessary docstring/comment" and the agent must JUSTIFY each instance, not silently bypass. The triggers PR established a small canon of priority-#3 justifications worth carrying forward:

- Public API rustdoc on a `pub` item under `missing_docs = "warn"`: always priority #3 (the lint requires the doc to exist).
- Load-bearing cancel-safety contract documentation (e.g., `state_store.put` cancel asymmetry, the trigger dispatcher's "single attempt is atomic, between-attempts is cancellable" contract): always priority #3 because future maintainers MUST read it before modifying the supervisor.
- Borrow-pattern rationale (e.g., `dispatch_log`'s two-phase open: phase 1 `if is_none() { open; set Some }`; phase 2 `as_mut()` match with typed-Io-error fallback): priority #3 because the unreachable-arm typed-error is non-obvious and exists specifically to satisfy AGENTS.md "no unwrap/expect outside tests".
- Test-step rationale comments (e.g., "Intentionally do NOT create the `missing` subdirectory; the open syscall must surface a typed Io error"): priority #3 because the comment names the NEGATIVE-space invariant that is not visible from the syntax alone; a future maintainer "fixing" the test by creating the directory would silently break the test's intent.
- Module-level `//!` doc comments that describe a dispatcher contract, atomicity model, or test convention: priority #3.

Comments that are NOT priority #3 and should be removed when the hook fires:
- "Changed from X to Y" / "Updated from..." / "Now this..." style memo comments.
- Test commentary that just restates what the next line of code does ("// Drop the handle to flush").
- Implementation history ("Originally we did A but switched to B").

### 7.10 What `compute_backoff` ergonomics tests must know

The supervisor's exponential-backoff function (`crates/aviso/src/watch/backoff.rs`) uses full jitter via splitmix64, base 250 ms, cap 30 s. Crucially, the jitter formula can legitimately return `Duration::from_nanos(0)` (the half-open `[0, ceil)` window includes 0). Any retry-cancel test that relies on the dispatcher pausing in a backoff sleep MUST inject a deterministic backoff via `dispatch_triggers_with_backoff` (the trigger dispatcher exposes this exact seam at `crates/aviso/src/watch/trigger/dispatcher/mod.rs`) rather than rely on the production `compute_backoff`. The convention in `dispatcher/tests.rs`: `|_| Duration::from_millis(100)` for success-after-retry tests (paired with `tokio::time::pause` + `advance(Duration::from_millis(101))` per retry), and `|_| Duration::from_secs(60)` for parent-cancel-during-backoff tests (the cancel arm must win against an unresolvable sleep). Future trigger work (webhook PR-G2, email PR-G3) or supervisor retry tests should follow the same pattern.
