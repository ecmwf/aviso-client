# aviso-client suite, plan v0.3

Client suite for [`aviso-server`](https://github.com/ecmwf/aviso-server), ECMWF's notification service for data-driven workflows. Three surfaces (Rust library, Rust CLI, Python package via PyO3) over one core implementation.

This is the current plan. Architectural decisions referenced by id (`D1`, `D2`, and so on) are defined in [`../docs/src/internals/decisions.md`](../docs/src/internals/decisions.md).

---

## 1. Server-side facts that drive design

All verified from the `aviso-server` source. These constraints determine the client architecture.

| Concern | Reality on the server | Client implication |
|---|---|---|
| SSE event format | `event: <type>\ndata: <json>\n\n`, **no `id:` line** | Standard `Last-Event-ID` reconnect does not apply. Sequence is extracted from the CloudEvent `id` field. |
| Resume parameters | `from_id` (inclusive sequence) and `from_date`, mutually exclusive, in the POST body | Persist `(stream_key, last_committed_sequence)`; reconnect with `from_id = last_committed_sequence + 1`. |
| Connection lifetime | Server intentionally closes after `connection_max_duration_sec` (default 3600 s), emitting `connection-closing` with `reason: "max_duration_reached"`. Other reasons: `server_shutdown`, `end_of_stream`. | Reconnects are routine, not failures. Must NOT trigger error backoff. |
| Heartbeats | `heartbeat` event every `sse_heartbeat_interval_sec` (default 30 s). | Monitor liveness; absence beyond `max(3 × interval, interval + 30 s)` triggers a reconnect. |
| Event types on the wire | `live-notification`, `replay`, `heartbeat`, `connection-closing`, `error`, `replay-control` | Six frame kinds; client uses a typed model. |
| Correlation | `X-Request-ID` header on every response, also embedded in the first SSE event and every error/control payload | Surface in client logs so users can quote it when filing issues. |
| Endpoints | `POST /api/v1/notification`, `POST /api/v1/watch`, `POST /api/v1/replay`, `GET /api/v1/schema[/{event_type}]`, `DELETE /api/v1/admin/{wipe/stream,wipe/all,notification/{id}}`, `GET /health`, `GET /metrics` (separate port) | Small, stable surface. |
| Auth | OpenAPI declares `bearer_jwt` and `basic`; server `direct` mode forwards Basic to auth-o-tron, `trusted_proxy` mode validates Bearer JWT locally | Client supports both Basic and Bearer; sources composable (env, file, explicit). |
| Schemas | `GET /api/v1/schema` returns identifier rules per stream | Discovery only (no client-side validation; the server is the single source of truth). |
| Wire payload | CloudEvent JSON. Each notification has `id = <event_type>@<sequence>`, `source = base_url`, `type = int.ecmwf.aviso.<event_type>`, `time`, `data = {identifier, payload}` | Client hides the CloudEvent envelope; users see a `Notification` type. Sequence is parsed from `id` via `rsplit_once('@')`. |

## 2. Architecture summary

Cited by ADR id; full rationale in [`docs/src/internals/decisions.md`](../docs/src/internals/decisions.md).

- **D1**: one Rust core (`aviso`), two peer consumers: the `aviso-cli` Rust binary and the `aviso-py` PyO3 extension. Core never depends on actix, PyO3, or CLI machinery.
- **D2**: reconnect-as-norm with at-least-once delivery. Per-resume-key `last_committed_sequence` advances only after all required triggers succeed. Watch state machine is `ReplayPhase × ConnectionStatus`, single reducer.
- **D3**: resume key is a hash of normalized base URL, event type, canonical filter body, schema fingerprint, key format version.
- **D4**: `StateStore` trait. `MemoryStore` plus a single-process `JsonFileStore` (atomic temp-write and `fsync`) ship in Phase 2 so the CLI can resume across restarts. Multi-process hardening (advisory file lock and monotonic-cursor merge) defers to Phase 3. The trait is the extension point; no other backends are planned.
- **D5**: `reqwest` with `rustls-tls`. SSE via the owned parser-only `crates/finesse` (WHATWG conformant, sync push-based, no I/O); our own reconnect loop (high-level SSE crates assume `Last-Event-ID`, which aviso does not honour).
- **D6**: `tokio`.
- **D7**: no client-side schema validation. Server is the single source of truth; client surfaces server errors verbatim with `X-Request-ID` correlation. `GET /api/v1/schema` is exposed only for human discovery (`aviso schema list`/`get`).
- **D8**: `AuthProvider` async trait. `Basic`, `Bearer`, `Env`, `ConfigFile`, `Chain`. Refresh on 401, retry once. Tokens never logged. Env prefix `AVISO_*`.
- **D9**: CloudEvent envelope hidden. Sequence from `<event_type>@<sequence>` via `rsplit_once('@')`. A malformed id is a terminal `ClientError::MalformedEvent`, not a reconnect (avoids livelock).
- **D10**: Rust public API is for Rust users; not constrained for hypothetical FFI. A C/C++ surface, if ever needed, is a separate adapter crate.
- **D11**: triggers are `echo` (stdout) and `log` (file), implemented in Rust core. Dispatcher is an internal `enum`; no public trait until a third type appears. Required vs optional triggers; per-trigger timeout, bounded retry; required failure stops the listener.
- **D12**: logging per ECMWF Codex Observability.md. Libraries emit `tracing` events, the binary owns subscriber init, JSON to stderr, redaction at emission, single-boundary log discipline. Strict OTel formatter is a follow-up.
- **D13**: Apache-2.0; per-file ECMWF copyright headers are optional in v0.1.
- **D14**: metrics deferred. Reserved namespace `aviso_client_*` (kept distinct from `aviso_server_*` for joint scraping). Banned labels documented.
- **D15**: watch state machine is the orthogonal product `ReplayPhase × ConnectionStatus`, single reducer, fields private.
- **D16**: `notify()` is NOT auto-retried on ambiguous transport failure (avoids duplicate publish).
- **D17**: `from_date` is bootstrap-only; converts to sequence cursor after the first commit.

## 3. Phased roadmap

Each phase is sized for one PR or a tight series, with a real demo at the end. "Done" requires CI green on every check, not just the new feature.

### Phase 0. Bootstrap

- Workspace skeleton (`aviso`, `aviso-cli`, `aviso-py`), all building.
- mdBook skeleton with `SUMMARY.md` taxonomy.
- `pyproject.toml` (maturin backend, scaffold).
- CI: `cargo fmt --check`, `cargo clippy --locked -D warnings`, `cargo test --locked`, `mdbook build`, `mdbook test`, `cargo deny check`, `docker compose config`.
- `tests/e2e/` docker-compose pointing at the prebuilt ECMWF aviso-server image (`eccr.ecmwf.int/aviso/aviso_server:0.5`), with a mounted test config that disables auth, pins the in-memory backend, and shortens heartbeat and connection-lifetime to surface reconnect bugs quickly. `AVISOSERVER_APPLICATION__BASE_URL` tracks `AVISO_SERVER_HOST_PORT` so parallel shards stay self-consistent.
- AGENTS.md rules: lints/errors/typing/ownership rules from the start, plus the time-bound-references rule (phase numbers live only in `plans/`) and conventional-commits rule (one concern per commit, every commit on `main` passes the full check set).
- First ADR set (D1 through D17).

Out of scope: any client behaviour. **Done when**: a fresh clone passes the CI commands above.

### Phase 1. Rust core (non-streaming)

- `AvisoClient`: `notify`, `schema`, `schema/{event_type}` pass-through, admin endpoints.
- `AuthProvider` (async) plus `Basic`, `Bearer`, `Env`, `ConfigFile`, `Chain`.
- `ClientError` (thiserror) with `X-Request-ID` correlation surfaced.
- `Notification` and `NotificationRequest` types; CloudEvent sequence extraction.
- Conservative `notify()` retry policy (D16).

Tested with `wiremock`. Property tests on CloudEvent id parsing. Docs for usage and auth.

### Phase 2. Streaming and checkpoint semantics

- Owned WHATWG SSE parser in a workspace crate (`crates/finesse`, named for the SSE that hides in the middle of the word, `publish = false` until a second consumer materialises) behind our own typed `SseEvent` enum. The existing parser-only crates on crates.io are either too fresh to depend on (`sse-core`, three weeks old at the time of decision, 63 downloads), maintenance-cold for four years (`eventsource-stream`, `async-sse`), or wrap their own reconnect logic that conflicts with our resume model (`reqwest-eventsource`, `eventsource-client`). `sse-codec` (MPL-2.0, 300k recent downloads, last release 2026-02-12) is the one viable third-party option; we picked the owned route to keep the critical path under our control and to give the parser room to evolve with `aviso-server`'s event taxonomy. D5 is amended to name the owned `finesse` crate.
- Reconnect supervisor with the classifier (D2). Single-boundary log discipline.
- Watch state machine per D2 and D15.
- `StateStore` trait plus `MemoryStore` plus a single-process `JsonFileStore` (atomic temp-write and `fsync`, but no cross-process locking yet). Pulled forward from Phase 3 because the CLI needs file-backed resume from day one: a user who runs `aviso watch`, stops the binary, and runs it again expects to pick up at the last committed sequence, not to start over. D4 amended in the same PR.
- `HistoryGap` typed error from `notification_replay_limit_reached`.
- Trigger dispatcher plus `Echo` and `Log` (D11), wired into checkpoint policy.
- Observability via `tracing` events at every state transition (connection open, connection close with reason, heartbeat starvation, replay phase boundaries, trigger outcomes, fatal). No client-side metrics surface; D14 is amended from "reserved namespace, deferred impl" to "tracing-only; metrics are a consumer concern". If a real consumer later needs a Prometheus or OTel metrics facade, it lands as a small opt-in follow-up against the `metrics` crate facade, not as a hard dependency.


Tested with a `wiremock` chunked-response harness plus kill-every-200ms stress, heartbeat-starvation, drop-during-replay, schema-fingerprint-change, replay-limit-mid-stream tests.

Public streaming API is **not** declared stable here. That happens at the end of Phase 3.

### Phase 3. Resume persistence: multi-process hardening

The single-process `JsonFileStore` (atomic temp-write plus `fsync`) ships in Phase 2 so the CLI works from day one. Phase 3 takes the multi-process correctness work that was originally bundled with it:

- Cross-process advisory file lock (`fs2` or `fd-lock`).
- Monotonic-cursor merge: before overwriting a key, read the on-disk checkpoint and commit only if the new sequence is at least the existing one. Protects against two processes racing on the same key.
- Kill-during-write fuzz harness: spawn N processes that write concurrently, SIGKILL them mid-write, assert the file always parses and no checkpoint goes backwards.
- `client.resume.applied` `INFO` log on resume from stored state.

Done when streaming API is stable; Phase 2 and Phase 3 tests all pass.

### Phase 4. Rust CLI

- Subcommands: `notify`, `watch`, `replay`, `schema {list,get}`, `admin {wipe-stream,wipe-all,delete}`, `auth check`, `config dump --redact`.
- YAML config plus `AVISO_CLIENT_CONFIG_FILE` override plus `AVISO_CLIENT_*` nested env vars.
- Default config file: `~/.config/aviso/config.yaml`.
- Default state file: `~/.config/aviso/state.json` (consumed by `JsonFileStore` from Phase 2). Both paths overridable via flags (`--config <path>`, `--state-file <path>`) and env vars (`AVISO_CLIENT_CONFIG_FILE`, `AVISO_STATE_FILE`). One directory for both config and state by design: simpler, one place to back up, consistent across Linux / macOS / Windows even where each platform has its own native convention.
- `--yes` required for destructive admin commands.
- `--ca-bundle <path>` for dev TLS; `--danger-accept-invalid-certs` loudly named with a WARN log.
- Graceful shutdown via cancellation tokens.

Tested with `assert_cmd`.

### Phase 5. PyO3 extension

- `AvisoClient` (async).
- `AsyncWatchIter`: manually implemented `__aiter__`/`__anext__` over `tokio::sync::mpsc`; owns a `CancellationToken`.
- `BlockingAvisoClient`: refuses if `asyncio.get_running_loop()` returns; context-manager required; `KeyboardInterrupt` cancels the Rust task.
- One tokio runtime shared per Python process.
- `pyo3-log` bridge, or a custom `tracing_subscriber::Layer` chosen based on backpressure and GIL ergonomics.
- `pyo3-stub-gen` type stubs.

Ends with one Linux wheel built in CI plus an import-smoke test.

### Phase 6. Wheel matrix

- `cibuildwheel`: Linux x86_64/aarch64 (manylinux plus musllinux), macOS universal2, Windows x86_64; `abi3` if supportable.

### Phase 7. Docs polish and examples

- Realistic end-to-end examples (MARS consumer, polygon spatial consumer, multi-listener daemon, respawn-survival demo).
- Troubleshooting expansion.
- `mdbook test` of code blocks remains in CI.

### Phase 8 (deferred). C++ FFI surface

Only on user request. The Rust API is not constrained for it (D10); a future adapter crate translates.

## 4. Follow-ups carried forward

Surfaced by the Oracle reviews and reflected in the roadmap. None gate any phase boundary; they are quality and scope items to revisit when the moment is right.

- `mdbook-linkcheck` (or an equivalent guard) so a broken cross-page anchor fails CI instead of being found by hand.
- Windows on the CI matrix, when the first platform-sensitive code lands (file locking, paths, signal handling). Required by Phase 6 wheels regardless.
- Strict OpenTelemetry-aligned log formatter. The current CLI emits `tracing_subscriber::fmt::json()` which uses tracing's own schema. Pick OTel-shaped JSON when a consumer requires it.
- Per-file ECMWF copyright headers, if ECMWF policy requires them. Currently the LICENSE file plus SPDX in each `Cargo.toml` carries the licensing.
- A server-side replay-summary signal carrying `{requested_cursor, oldest_available_sequence, replayed_count, complete: bool}`, to revisit only if replay observability hits a real ceiling. The client ships in "completeness unknown" mode without it and degrades cleanly. (A validator-version response header was considered too; it is moot now that D7 dropped client-side validation.)
- Idempotency-key contract for `POST /api/v1/notification`. Without it the client refuses to auto-retry ambiguous transport failures (D16).
- An `AVISO_LOG` malformed-directive test once the CLI has runtime tests.

## 5. Open questions

None gate ongoing work. Tracked here so they remain visible across compactions.

- Should `BlockingAvisoClient` provide a context-manager-only API, or also a plain class with explicit `close()`? Pick during the Phase 5 spike.
- When the Python bridge eventually wires logging, choose between `tracing_log` to `log` to `pyo3-log`, or a custom `tracing_subscriber::Layer` calling Python `logging` directly. Decide during Phase 5 based on backpressure and GIL behaviour.

### Resolved

- *Watch API shape*: settled as Stream-primary plus a thin `watch_with_handler` callback sugar that wraps the Stream. The Rust core exposes `impl Stream<Item = Result<Notification, ClientError>>` for idiomatic async iteration and a 20-line `watch_with_handler` for daemon-style consumers. Both surfaces drain the same internal `tokio::sync::mpsc` channel so reconnect, checkpoint, auth-refresh, heartbeat, and trigger behaviour stay identical across bindings. The decision is driven by the cross-language constraint that Python (PyO3, via `__aiter__`/`__anext__` over the channel) and a future C++ adapter (via callback registration on `watch_with_handler`) must both bind cleanly without reimplementing supervisor logic. The ADR for this decision (D19) lands with PR-E2a where the API ships.

- *Fan-out across consumers of a single watch*: settled as single-consumer. The supervisor uses `tokio::sync::mpsc::channel(N)` internally; `client.watch(req)` returns a `NotificationStream` that is not `Clone`. Anyone wanting one watch to feed multiple consumers can tee via `tokio::sync::broadcast` themselves. The single-consumer choice keeps checkpoint advancement and trigger semantics unambiguous (one consumer means one well-defined commit point) and keeps bindings simple (PyO3 and a future C++ adapter each bind one channel per call). A future broadcast-based API can ship later without breaking single-consumer callers if a concrete need surfaces. Captured by the same ADR D19 as the watch API shape.

- *Multi-listener support across a single `AvisoClient`*: one client can drive any number of concurrent `watch()` calls; each produces an independent supervisor with its own HTTP connection, checkpoint slot, and (in PR-F) trigger pipeline. Resource sharing happens cleanly at the appropriate layers (`reqwest::Client` connection pool, `Arc<dyn AuthProvider>` for shared auth state with refresh propagation, `Send + Sync` `StateStore` for per-key write serialisation). D3 guarantees per-listener resume-key uniqueness across distinct (event_type, filter, schema_fingerprint) tuples. PR-E2a keeps `AvisoClient` `Send + Sync + Clone`, logs a `WARN` on resume-key collision (a misuse signal, not a hard error), and ensures `AvisoClient::Drop` cancels all child supervisors via a parent `CancellationToken`. Server-side capacity policies (per-user, per-role) are out of the client's scope and handled at the proxy or aviso-server layer. The ADR for this decision (D20) lands with PR-E2a.

- *PyO3 spike timing*: settled as defer to Phase 5. The eight-test spike was insurance against the risk that a closure-heavy or lifetime-bound Rust API would not bind cleanly into Python's `asyncio` model. The Option C resolution above (Stream over `mpsc` channel) is the textbook PyO3 async pattern with explicit `pyo3-async-runtimes` support, so the design risk the spike was sized to surface is substantially eliminated. The three residual concerns (Stream `Drop` cleans up the supervisor task; channel is bounded for backpressure; supervisor uses the ambient runtime rather than spawning its own) become design constraints on PR-E2 rather than a separate validation PR. PR-E2b includes a Rust integration test asserting that dropping the Stream mid-iteration tears down the supervisor task within a bounded time.

- *PR-E2 split*: PR-E2 is split into PR-E2a and PR-E2b along the seam between the happy-path data path and the resilience layer. PR-E2a ships the public API (`WatchRequest`, `AvisoClient::watch`, `watch_with_handler`) plus the supervisor's single-connection happy path; PR-E2b adds the reconnect loop, auth refresh, heartbeat watchdog, HTTP-status mapping, and `StateStore` integration. Two medium PRs are preferable to one large one because the API shape gets reviewer feedback before the resilience layer is built on top of it, and because each PR fits inside a single review cadence. See §6 for the per-PR scope details.

- *Checkpoint advancement in PR-E2b interim policy*: supervisor-side, on next send. The supervisor holds the last-sent-but-not-yet-committed sequence; before sending item N+1 it commits item N to the `StateStore`. The user-facing "commit on next pull" contract holds: pulling item N+1 implies item N is durable. No public API change. PR-F replaces "on next send" with "after triggers succeed"; the swap is internal and does not break callers.

- *Parent-cancellation primitive for `AvisoClient::Drop`*: `Arc<DropGuard>` wrapping `tokio::sync::watch::Sender<bool>`. The last-clone drop fires the watch; each supervisor holds a `watch::Receiver` and `select!`s on `wait_for(|v| *v)` alongside its per-stream oneshot. No new workspace dependency; tokio's `sync` feature already covers `watch`.

- *User-supplied `from` versus stored checkpoint*: user `from` always wins when supplied. The `StateStore` checkpoint is consulted only when `WatchRequest` has no `from`. At-least-once delivery is preserved at the `StateStore` layer (re-delivering a committed item just re-commits the same value); the "library does not second-guess the user's explicit request" contract is preserved at the API surface.

- *`Retry-After` header on 429 / 503*: honoured with a 5-minute sanity cap. Parse delta-seconds or HTTP-date; sleep at least `min(header_value, 5 minutes)`. Falls back to the standard exponential backoff schedule when the header is absent or unparseable.

- *Schema fingerprint detection*: deferred entirely. The auto-derived resume key uses `schema_fingerprint = None`. The server does not emit fingerprints on the wire (the `dataschema` URL is the same string every time), and D7 already says client-side validation is not the library's concern. The `FatalKind::SchemaFingerprintChanged` reducer variant stays as harmless producer-side dead code; it costs nothing because `#[non_exhaustive]` and can be removed in a later polish PR if it bothers anyone.

- *Auth refresh scope*: every fresh connection attempt (initial AND every reconnect) gets the D8 refresh-then-retry-once treatment. The reducer's `RefreshingAuth` state guards against infinite loops within a single attempt. Long-lived watches survive token expiry that happens during reconnect N; the alternative (initial-only) would terminate the watch unrecoverably when a token expires mid-session.

- *Backoff jitter*: full jitter, `delay = random_uniform(0, base * 2^attempt) capped at 30s`. Randomness sourced from `Instant::now().elapsed().subsec_nanos()` so no `rand` dep is added. Good enough for spreading retries; backoff jitter does not need cryptographic randomness.
